## Goal

iOS/Android 플랫폼 정책 요구사항 중 **마감일이 있는 것**을 공식 문서 실시간 조회로 확인하고, 각 요구의 **마감일·프로젝트 현재값·충족 여부**를 D-day 축으로 정리한 **advisory 리포트**를 낸다. 동시에 정책이 만들어내는 요구사항을 기계 판독 가능한 **핸드오프 파일**로 남겨 형제 스킬 `currency`가 권장 버전 게이트의 하한으로 쓰게 한다.

리포트가 답하는 질문은 "최신이 몇이냐"도 "무엇으로 올려야 하나"도 **아니다**. **"언제까지 무엇을 해야 하고, 지금 그게 됐나"**다.

- **스킬명:** `platform-watch`. 3스킬 플러그인 `rn-upgrade-kit`의 첫 번째 — 나머지 둘은 `currency`(설계 완료, 정본 `seed/rn-currency-SKILL.md`), `rehearsal`(설계 완료).
- **위치:** `currency`가 registry 축(버전)에서 "뭘로 올려야 하나"를 산정하고 `rehearsal`이 그걸 실제로 돌려본다면, 이 스킬은 **날짜 축**에서 "언제까지 뭘 해야 하나"를 감사한다. seed §1 Track C가 이 스킬의 전신이며, seed가 "registry에 아예 없다 — 웹 조회가 유일한 경로"라고 적어둔 트랙이 통째로 분리된 것이다.
- **advisory 전용.** 코드·`package.json`·네이티브 설정·`.gitignore`를 어떤 경로로도 수정하지 않는다. 쓰기는 리포트 · 상태 파일 · 핸드오프 파일 셋뿐이다.

## 정체성 — auditor 정본 · watcher 마킹 레이어 (라운드 1)

**리포트는 매번 전수 감사다.** 재실행하면 현재 시점의 전체 목록이 다시 나온다. 상태 파일은 각 항목에 **델타 배지를 다는 용도로만** 쓰인다.

```
전수 감사 (정본)  ←  상태 파일 (표기 전용, 판정 근거 아님)
```

### 상태 fail-safe

상태 파일이 **없거나 · 깨졌거나 · 구버전 스키마**인 경우:

- 전수 리포트는 **정상 산출된다.**
- 델타 배지만 생략된다.
- 이건 오류가 아니라 정의된 degrade 경로다.

이 fail-safe가 정체성의 실체다. 상태 손실이 산출물을 바꾸지 않으므로, 이 스킬은 상태를 들고도 `rehearsal`의 무상태 원칙과 충돌하지 않는다.

### 상태가 판정에 새어드는 통로 차단

- 소스 내용 검증(§소스 도달 모델)은 **자기 완결적**이어야 한다. 이전 스냅샷과 diff하면 무상태 원칙이 뒷문으로 깨진다.
- 소스 도달 실패 시 직전 스냅샷의 날짜를 **폴백으로 쓰지 않는다** (§소스 도달 모델).

- 등급 임계일은 항목별로 덮어쓸 수 있되 **기본값을 스킬 본문에 적지 않는다** — 공유 상수 한 곳(§구현자 미확정 해소)에서 온다.

### enum 밖 발견물 — `[미분류]`

조회 중 enum에 없는 마감을 발견하면:

- **리포트에는 반드시 실린다.** 빼지 않는다.
- 동일성 키가 없으므로 **델타 마킹만 생략**하고 `[미분류]`로 표기한다.
- 같은 항목이 반복 등장하면 리포트 말미에 **enum 승격 후보**로 제안한다 — 사용자가 참조 파일을 늘릴 신호가 필요하다.

## 동일성 키 & 마킹 어휘 (라운드 2)

### 동일성 키 = enum 슬러그

- **URL·제목은 근거 필드일 뿐 키가 아니다.** 정책 페이지 개편·문구 변경이 마킹을 깨뜨리지 못한다.
- **임계값은 키가 아니라 필드다.** `targetSdk 36 → 37`은 새 항목이 아니라 같은 항목의 `[변경]`이다.
- 리포트 각 항목에 **슬러그를 함께 출력**한다 — `--target` 인자가 내부 식별자 노출이 아니라 이미 보이는 값의 재사용이 되고, `[변경]` 마킹의 근거로도 기능한다.

### 마킹 어휘 — 3값 고정

| 마킹       | 의미                                                     |
| ---------- | -------------------------------------------------------- |
| `[신규]`   | enum 항목이 이번에 처음 마감을 가짐                      |
| `[변경]`   | 임계값·날짜 등 필드가 움직임 — **이전값→현재값 병기**     |
| `[미분류]` | enum 밖 발견물 — 키 없음                                 |

**변화 없는 항목은 마킹 없이 그대로 나온다.** 4번째 어휘를 늘리지 않는다 — 어휘가 늘면 마킹의 신호 대 잡음이 무너진다. (`rehearsal`의 판정 어휘 3값 고정과 동형.)

## 날짜 신뢰 모델 (라운드 3)

**스킬은 날짜를 만들지 않는다.** 인용 가능한 것만 날짜로 인정한다.

| 원문 형태                              | 표시                  | D-day  | 정렬 키           |
| -------------------------------------- | --------------------- | ------ | ----------------- |
| 일 단위 (`"August 31, 2026"`)          | `D-113`               | 계산   | 그 날짜           |
| 월·분기 단위 (`"starting April 2026"`) | 원문 그대로 `2026년 4월` | 미계산 | **그 기간의 초일** |
| 규칙 표현 (`"one year after …"`)       | —                     | 미계산 | 정렬 축 밖        |
| 날짜 언급 없음 / 소스 도달 실패        | —                     | 미계산 | 정렬 축 밖        |

- **정렬·표시·D-day는 세 축이다.** 한 필드로 뭉치지 않는다.
- **저정밀 날짜의 정렬 기준은 초일이다.** `"starting April 2026"`은 4/1부터 발효이고 사용자가 대비를 마쳐야 하는 시점도 4/1이다. 말일 기준이면 최대 29일 낙관 편향이 생겨 확정 마감보다 뒤로 밀린다 — **마감 추적 스킬에서 낙관 편향은 단방향 손해다.**
- 허용되는 유일한 산술은 `오늘 − 인용된 절대 날짜`다.
- 규칙 표현을 해석해 추정 날짜를 만들지 않는다. 추정이 본문에 실리면 환각 금지 선이 흐려진다.

### 셸 의존 0

- D-day 계산에 `date`를 **호출하지 않는다.** 컨텍스트의 현재 날짜를 쓴다.
- 근거: seed §3의 `date -v-14d`가 BSD 전용이라 다른 호스트에서 깨지는 전례가 이미 있다.

## 소스 도달 모델 (라운드 5)

**조용한 실패가 가장 위험하다.** fetch 실패로 항목이 리포트에서 빠지면 사용자는 "마감이 없어졌다"고 읽는다.

### 2단 URL — 독립성 요건

enum 항목마다 참조 파일에 1차·2차 URL을 둔다.

- **2차 URL의 요건은 독립성이다.** 1차의 미러나 같은 사이트 하위 경로면 같은 개편에 함께 죽어서 이중화가 아니다. **다른 호스트 또는 다른 성격의 공식 페이지**여야 한다 (예: 1차 `developer.android.com` 정책 본문 / 2차 Play Console 고객센터 문서).
- 이 요건을 참조 파일 스키마에 명시한다 — 나중에 URL을 추가할 때 지켜지게.

### "1차 실패"에 내용 실패를 포함한다

HTTP 200이어도 그 페이지에서 해당 enum 항목이 요구하는 재료(임계값·날짜 문구)를 못 찾으면 **실패로 취급하고 2차로 넘어간다.**

> 리다이렉트로 무관한 페이지를 받아 거기서 아무 숫자나 읽는 것이 이 스킬의 최악 실패다.

- 내용 검증은 **자기 완결적 검사**여야 한다 — "이 페이지에 이 항목의 재료가 있는가"만 본다.
- **이전 스냅샷과 비교하지 않는다.** 비교하면 §정체성의 무상태 원칙이 깨진다.

### 둘 다 실패

1. 웹검색으로 새 URL 후보를 찾는다 — **상한 N개** (구현 재량, 제안 3).
2. **자동 채택하지 않는다.** `URL 이동 의심: <후보>`로 리포트에 올려 사용자가 참조 파일을 고치게 한다.
3. **후보에서 값을 읽어 리포트 본문에 쓰는 것은 금지한다.** 후보는 주소일 뿐 근거가 아니다.
4. 해당 항목의 판정은 후보 유무와 무관하게 `확인 못 함 (소스 도달 실패)`다.

## 등급 & 리포트 구조 (라운드 6)

### 등급 = f(D-day, 충족 여부) — 순수 함수

seed §4의 🔴🟠🟡⚪는 **강제성 × 임박도** 2축이었다. 확정 사항 1·7이 추적 대상을 "마감일 있는 것"으로 잘랐으므로 **강제성 축이 붕괴했다.** 두 번째 축은 강제성이 아니라 **충족 여부**다 — 이미 targetSdk 36을 맞췄다면 D-113이어도 할 일이 없다.

| 등급 | 조건                                          |
| ---- | --------------------------------------------- |
| 🔴   | 미충족 · D-day ≤ 임계일                       |
| 🟠   | 미충족 · D-day > 임계일 (또는 저정밀 초일 기준) |
| ✅   | 이미 충족                                     |
| ⚠    | 어느 축이든 확인 못 함                        |

- 이모지는 **스캔용 시각 보조**일 뿐 새 정보를 넣지 않는다. 독립 판정이 아니다.
- 🟡·⚪는 날짜 축에서 의미가 없어 **폐기**한다.
- **임계일 90은 임의 기준이다.** `shared/constants.md`의 `grade_threshold_days`에 조정 가능한 값으로 한 곳에만 둔다(항목별 덮어쓰기는 `references/watch-targets.md`). targetSdk 대응은 RN 업그레이드를 동반할 수 있어 90일도 넉넉하지 않다 — 사용자가 늘릴 수 있어야 한다.
- **핸드오프 `urgency`가 이 함수의 🔴/🟠 분기를 그대로 쓴다** (§핸드오프 계약). 같은 항목이 리포트에서 🔴인데 핸드오프에서 `여유`인 상태는 발생할 수 없다 — 두 출력이 같은 계산에서 나온다.

### 리포트 4블록

| 블록                          | 정렬                | 등급  |
| ----------------------------- | ------------------- | ----- |
| 1. 미충족                     | D-day 오름차순      | 🔴 🟠 |
| 2. 확인 못 함                 | D-day 정렬 축 **밖** | ⚠     |
| 3. 이미 충족                  | 하단 별도 블록      | ✅    |
| 4. 미조회 (사용자 지정 스코프) | 별도 블록           | 없음  |

- **✅를 미충족과 같은 정렬에 섞지 않는다.** 섞으면 D-day 오름차순이 "급한 것 먼저"를 못 지킨다.
- **✅ 항목도 리포트에서 빼지 않는다.** "점검했는데 통과"와 "점검 안 함"은 구분돼야 한다.
- **⚠는 사용자가 할 일로 갈라 적는다:**
  - `마감일 확인 못 함 (소스 도달 실패 / 저정밀 날짜 / 규칙 표현)` → **참조 파일 수리**
  - `현재값 확인 못 함 (경로 부재)` → **프로젝트 설정 확인**
- **블록 4를 ⚠와 절대 섞지 않는다.** ⚠는 사용자가 할 일이 있는 상태로 정의됐다. 미조회는 사용자가 스스로 뺀 것이라 할 일이 없다. 항목이 많으면 슬러그 나열 한 줄로 압축해도 된다.

### 정합성 = 같은 원칙의 일관된 적용

`rehearsal`의 Windows 거부 사유는 **"Windows"가 아니라 "네이티브 빌드 실행"**이다. 원칙은 *"검증 못 한 실행 경로를 사실로 쓰지 않는다"*이고, 이 스킬에는 그런 경로가 **없다** — 웹 fetch + 텍스트 파일 Read + 마크다운 Write가 전부다. 원칙은 같고 적용 결과만 다르다.

- **`currency`의 ✅도 같은 계열이지만 근거 문장이 다르다** (`currency` 라운드 4 → 2026-08-09 실측으로 정정). 위 표의 `currency` 행은 이 스펙 작성 시점에는 근거 없이 적힌 값이었고, 라운드 4가 *셸 의존 0*으로 사후에 참으로 만들었다. 그런데 스펙 리뷰의 실측에서 **registry full packument를 WebFetch로 못 읽는다**(절단)는 게 드러나 `currency`는 배포일 획득에 `node -e` 한 줄을 되찾았다.
  - **결론은 안 바뀐다** — `node`는 대상이 RN 프로젝트라 항상 있고 호스트·PM에 무관하며 Windows Git Bash에서도 돈다. 제거된 건 `pnpm`·`jq`·`date -v-14d`(BSD 전용) 의존이고 그건 그대로 제거된 상태다.
  - **이 스킬은 여전히 셸 의존 0이다.** `currency`와의 차이는 registry 배포일이라는 재료가 이 스킬엔 없기 때문이지 원칙이 달라서가 아니다.
  - 표의 세 행은 *조회만 / 조회+node 1줄 / 네이티브 빌드 실행*이라는 성격 차이에서 나온다.
- **Windows에서도 iOS 항목을 판정한다.** `Podfile`·`project.pbxproj`·`xcconfig`는 repo 안 텍스트라 Xcode 없이 읽힌다. **판정 가능한 것과 빌드 가능한 것은 별개다.** 이걸 명시하지 않으면 Windows 사용자가 "윈도우니 iOS는 스킵되겠지"라고 오해해 미충족을 놓친다.
- README 지원 매트릭스에 **거부 사유까지** 적는다 — "rehearsal: POSIX 전용 — 네이티브 빌드를 실제 실행하기 때문", "platform-watch·currency: 전 호스트 — 조회·파일 읽기만". 스킬별 차이가 임의가 아니라 **실행 유무에서 나온다**는 걸 보여줘야 사용자가 규칙을 기억한다.

## 스코프 인자 (라운드 8)

`--platform android|ios` · `--target <enum 슬러그>` — **좁히기 전용.**

- 기본값은 항상 전체다. **넓히는 방향의 인자는 두지 않는다.**
- 제외된 항목은 조용히 빠지지 않고 **블록 4 `미조회 (사용자 지정 스코프)`**로 남는다. 전수 계약은 *"목록에서 안 사라진다"*로 유지되고 **조회만** 생략된다.
- 도입 근거: §소스 도달 모델의 수리 루프(URL 이동 의심 → 참조 파일 수정 → 해당 항목만 재확인)가 스펙에 실재하는 절차이고, 인자 없이는 매번 전수를 돈다. 좁히기 전용이라 새 판정·새 실패 모드를 만들지 않는다.
- **두 인자를 동시에 주면 AND(교집합)다.** 교집합이 공집합이면 빈 리포트가 아니라 `지정 스코프에 해당 항목 없음` + **유효한 슬러그 목록**을 낸다 — 잘못 친 인자가 조용히 빈 결과로 보이면 안 된다.
- **인자는 이 둘로 닫는다.** `--since`·`--format`·`--json` 같은 확장은 이번 버전 범위 밖이다. 좁히기 전용이라는 성질이 인자 하나 늘 때마다 약해진다.

### 좁힌 실행의 상태·핸드오프 병합 (인터뷰 후 추가 — 2026-08-09)

**좁힌 실행은 파일을 덮어쓰지 않고 병합한다.** `state.json`·핸드오프 둘 다.

| 파일 | 좁힌 실행의 동작 |
| --- | --- |
| `state.json` | 조회된 슬러그 엔트리만 갱신. **미조회 슬러그의 이전 엔트리는 보존한다** |
| 핸드오프 | 조회된 항목만 갱신. 미조회 항목은 이전 값을 그대로 싣되 **`stale: <마지막 조회일>`을 부착**. 파일 레벨 `scope`에 이번에 실제 조회된 슬러그를 적는다 |
| 리포트 | 병합하지 않는다 — 리포트는 이번 실행의 산물이고 미조회분은 이미 블록 4가 담당한다 |

> **추가 사유 (구멍 A3):** 핸드오프는 **전수** 계약이고(§핸드오프 계약 · AC) 그건 `currency`가 하한과 `current`를 전부 그 파일에서 가져가기 때문이다. 그런데 좁히기 인자는 제외 항목의 **조회 자체를 생략**한다. 덮어쓰기로 구현하면 `/platform-watch --target play/data-safety` 한 번이 `currency`의 `targetSdk`·iOS min·모든 정책 하한을 **조용히 증발**시킨다 — degrade 표기조차 없이 `플랫폼 하한 미반영`도 아닌 "그 항목이 원래 없었던 것"이 된다.
>
> `state.json`도 같은 모양이다. 덮어쓰면 미조회였던 슬러그가 다음 전수 실행에서 **`[신규]`로 오탐**된다 — 라운드 2가 동일성 키로 죽인 바로 그 실패다.
>
> **`stale`은 판정을 바꾸지 않는다.** `currency`는 낡은 하한도 그대로 적용한다(§핸드오프 계약 — 낡은 하한은 과소평가일 뿐이고 안 쓰는 쪽이 낙관 편향). `stale`은 표기용이다 — §정체성의 *"상태는 표기 전용, 판정 근거 아님"*과 같은 위상.

## 산출물 · 경로 (라운드 9)

```
.rn-upgrade-kit/
  platform-watch/
    reports/YYYY-MM-DD.md      ← 날짜별 누적, 보존 상한 N
    state.json                 ← 덮어쓰기 1개, 표기 전용
  handoff/
    platform-requirements.md   ← 소유: platform-watch / 독자: currency
  currency/…
  rehearsal/…
```

- **핸드오프는 스킬 하위가 아니라 공용 하위(`handoff/`)에 둔다.** 소유자는 `platform-watch`, 독자는 `currency`라 어느 스킬 폴더에 넣어도 한쪽에서 보면 남의 집이다. 소유자와 독자가 다른 파일은 중립 지대에 있어야 한다.
- **리포트·상태는 스킬 하위**가 맞다 — 소유자가 하나다.
- **핸드오프 경로는 문자열 상수로 한 곳에 고정**하고 두 스킬 스펙이 그걸 참조한다. 양쪽에 각각 적으면 나중에 한쪽만 바뀌어 조용히 끊긴다.
- **`.gitignore`를 수정하지 않는다.** README에 붙여넣을 한 줄(`.rn-upgrade-kit/`)만 제시한다. 이력을 남기고 싶은 사용자는 그 줄을 안 넣으면 되므로, 리포트 커밋의 가치는 기본값을 바꾸지 않고도 얻어진다.
- **리포트 보존 상한 N=12** — 날짜별로 쌓이는데 지우는 주체가 없다. `rehearsal`의 artifacts N=3과 같은 모양이되, 마크다운 수 KB라 더 넉넉하게 잡는다(주간 실행 기준 약 3개월). 정리한 개수를 리포트 말미에 한 줄로 보고한다.
  - **`currency`와 같은 상수를 참조한다** (`currency` 라운드 9a). 두 advisory 스킬은 같은 매체(마크다운 수 KB)라 성격이 같다 — 각자 하드코딩하면 한쪽만 바뀌는 드리프트가 난다. `rehearsal`의 N=3은 매체가 다르므로(수십 MB) 성격에서 파생된 정당한 차이다.
  - 상수의 물리적 위치는 **플러그인 루트 `shared/constants.md`의 `report_retention_n`**으로 확정됐다 (인터뷰 후 — `.omc/specs/plugin-shell.md` §2). 스킬별 `references/`는 소유자가 하나라 공유물을 담을 수 없다 — 핸드오프를 `handoff/` 중립 지대에 둔 논리와 동일하다. `handoff_path`·`grade_threshold_days`·`url_candidate_limit`도 같은 파일에서 온다.
- **같은 날 두 번 실행하면 덮어쓴다** (`currency` 라운드 9c). 시각 suffix를 붙이지 않는다 — 붙이면 보존 상한 계산이 "12일"이 아니라 "12파일"로 흔들려 상한의 의미가 바뀐다. 스코프를 좁혀 돌렸어도 파일을 쪼개지 않는다(헤더의 스코프 줄이 그 사실을 담는다).

## 핸드오프 계약 (라운드 10)

### 번역은 `currency`가 한다

확정 사항 4의 두 문장("패키지 버전을 추천하지 않는다" + "RN 하한 요구를 파일로 남긴다")은 **번역 주체를 `currency`로 두면** 무모순이다.

- RN 하한 산정에 필요한 재료(RN 릴리즈 노트·registry·peer 정보)가 `platform-watch`에는 **설계상 없다**(확정 사항 3: 웹 조회가 유일). 재료 없는 쪽의 판정은 추측이 된다.
- "공식 문서가 명시하면 하한도 싣는다"는 조건부 분기는 **두지 않는다.** Android/Apple 정책 페이지가 React Native를 언급하지 않으므로 실질 발동률이 0에 가깝고, 희소 분기는 *"명시에 근접한 문장"을 명시로 읽는* 환각 압력을 만든다 — §날짜 신뢰 모델에서 죽인 실패 모양과 동형이다.

### 스키마 — 고정

`currency`가 파싱해야 하므로 자유 서술이면 안 된다.

#### 파일 레벨 메타 (인터뷰 후 추가 — 2026-08-09)

| 필드             | 값                                       | 소비자 요구                                      |
| ---------------- | ---------------------------------------- | ------------------------------------------------ |
| `schema_version` | `shared/constants.md`의 `handoff_schema_version` | `currency` degrade 2번(`플랫폼 하한 미반영 (스키마 불일치)`)이 **판별 가능해지려면 필요하다** |
| `generated`      | 이 실행의 날짜 (컨텍스트 현재 날짜)      | `currency`가 헤더에 `핸드오프 <생성일>`을 병기한다 |
| `scope`          | `전체` 또는 실제 조회된 슬러그 목록      | 좁힌 실행이 어디까지 갱신했는지 독자가 알아야 한다 (§스코프 인자 — 병합) |

> **추가 사유:** `currency` 스펙은 `핸드오프 <생성일>` 병기와 `스키마 불일치` degrade를 **Acceptance Criteria로 요구**하는데, 인터뷰 시점 스키마는 항목당 필드만 정의해 파일 레벨 메타가 없었다. 생산자 스키마에 없는 값을 소비자가 요구하는 상태였다. 항목 필드는 그대로다.

#### 항목당 필드

| 필드         | 출처       | 비고                                          |
| ------------ | ---------- | --------------------------------------------- |
| `key`        | 라운드 2   | enum 슬러그 = 동일성 키                       |
| `requires`   | 확정 1     | 요구 항목 + 요구값                            |
| `deadline`   | 라운드 3   | **정밀도 표기 포함** (확정/저정밀/미확인)     |
| `urgency`    | 인터뷰 후 추가 | `임박` / `여유` / `판정 불가`. **날짜를 소유한 쪽이 임박도도 판정한다** — 아래 |
| `current`    | 라운드 4   | 현재값 (충돌 시 병기, 미확인 시 명시). **`currency` 스냅샷 헤더의 유일한 공급원** — 아래 계약 5항 |

- **`rn_floor` 필드는 스키마에 아예 없어야 한다.** 필드가 있으면 채우려는 압력이 생긴다.

#### `urgency` — 임박도 공급 (인터뷰 후 추가 — 2026-08-09)

`urgency = f(deadline, grade_threshold_days)`. §등급의 🔴/🟠 분기와 **같은 함수·같은 임계일**을 쓴다.

| 값 | 조건 |
| --- | --- |
| `임박` | D-day ≤ `grade_threshold_days` |
| `여유` | D-day > 임계일, 또는 저정밀 날짜의 초일 기준이 임계일 밖 |
| `판정 불가` | D-day 미계산 (규칙 표현·미확인·소스 도달 실패) |

> **추가 사유 (구멍 A2):** `currency`의 등급표는 🔴 = "마감 임박 정책 하한", 🟠 = "여유 있는 정책 하한"으로 갈리는데, `currency`의 비목표는 *"정책 요구의 마감일 판정 — 날짜 축은 `platform-watch`"*다. 임계일 90은 이 스킬 소유이고 `status` 3값은 임박도를 안 실어 날랐다. 즉 `currency`가 **정의되지 않은 임계일로 날짜 산술을 다시 하는 수밖에 없는 상태**였고, 그건 두 스킬이 같은 항목에 다른 급박도를 말하는 경로다.
>
> 해법은 `rn_floor`를 안 둔 것과 **반대 방향의 같은 수법**이다 — 재료 없는 쪽이 채우게 만들지 말고, **재료 가진 쪽이 계산해 넘긴다.** `currency`는 `urgency`를 읽어 등급에 매핑만 하고 D-day를 계산하지 않는다.
>
> `urgency`는 **날짜 판정이지 버전 판정이 아니다.** `rn_floor` 금지선을 넘지 않는다 — 이 스킬은 여전히 RN을 언급하지 않는다.
- **미충족만 싣지 말고 전수로 싣는다.** 충족 여부는 `status` 필드로 구분한다. §정체성의 "항상 전수"와 정합적이고, `currency`가 "이미 충족"을 알면 하한 계산에서 제외 근거로 쓸 수 있다. 비용은 0이다.

### `currency` 쪽 계약 — **반영 완료 (2026-08-09)**

계약은 양쪽에 적혀야 성립한다. 아래 5항 전부 `deep-interview-currency.md` §핸드오프 — 독자 계약에 실렸다.

1. `currency`는 이 파일을 읽어 게이트의 **하한**으로 쓴다. (반영 시 정제: 하한은 게이트 목록에 추가되지 않고 **범위 축**이 된다 — 게이트 6개는 전부 하강 필터라 역방향 제약과 방향이 충돌한다. `currency` 라운드 1.)
2. 번역("targetSdk 36 → RN 0.7x")의 **근거 링크를 자기 리포트에 남긴다** — 확정 사항 6의 환각 금지가 `currency` 쪽으로 상속된다.
3. 번역 근거를 못 찾으면 하한을 만들지 말고 **`번역 확인 못 함`**으로 리포트에 남긴다.
4. 파일이 없으면 하한 없이 계산하고 **`플랫폼 하한 미반영`**을 리포트에 적는다.
5. **`current` 필드는 `currency` 스냅샷 헤더의 `targetSdk`·iOS 배포 타깃의 유일한 공급원이다.** `currency`는 그 값을 직접 파싱하지 않는다 (§현재값 읽기의 공유 참조 파일 철회가 이 항으로 대체됐다). 이 파일이 없으면 `currency` 헤더는 값을 비우지 않고 `— (핸드오프 없음)`으로 사유를 병기한다.

> 계약이 **양방향 의존이 되지 않는다**는 점에 주의. 5항은 `currency`가 이 파일에서 값을 *더 가져간다*는 뜻일 뿐, 이 스킬이 `currency`에 무엇을 요구하지 않는다. 단방향은 유지된다.

### 번역 결과 3값 (`currency` 라운드 3 — 참고)

`currency`가 이 파일의 `requires`를 버전 하한으로 옮길 때 결과가 항상 하한인 것은 아니다. **`targetSdk`는 RN이 아니라 앱 `android/build.gradle`이 정하기 때문**이다.

| 결과 | 이 스킬 입장에서의 의미 |
| --- | --- |
| 하한 있음 | 요구 충족에 패키지 업그레이드가 필요 |
| **하한 불요 (프로젝트 설정 축)** | 요구가 설정 한 줄로 충족 — `currency`가 아니라 사용자가 할 일 |
| 번역 확인 못 함 | 근거 미발견 — 하한 없음 |

두 번째 결과는 이 스킬의 `status: 미충족` 항목이 **버전 문제가 아닐 수 있다**는 뜻이다. 이 스킬은 그 판별을 하지 않는다(재료가 없다) — 기록해 두는 이유는 리포트 독자가 두 스킬을 함께 읽을 때 혼동하지 않게 하기 위함이다.
