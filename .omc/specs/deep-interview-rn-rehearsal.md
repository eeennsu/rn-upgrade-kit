## Goal

격리된 git worktree에서 지정한 React Native 버전으로의 업그레이드를 **실제로 끝까지 수행**하고, 티어별 통과·실패·미실행 판정과 재현 커맨드 시퀀스를 담은 **리포트 하나**를 낸 뒤 worktree를 폐기한다. 사용자 작업 브랜치·소스·`package.json`·네이티브 설정은 어떤 경로로도 수정하지 않는다.

리포트가 답하는 질문은 "이 업그레이드가 안전한가"가 **아니다**. "우리 프로젝트에서 이 업그레이드를 시도했을 때 **어디까지 갔고 어디서 멈췄나**"다.

리허설이 **모든 게이트를 통과한 경우에 한해**, 검증된 결과를 폐기하지 않고 전용 브랜치로 남기는 **채택(adopt) 종단 옵션**을 제공한다 (§채택). 채택도 사용자 작업 브랜치를 수정하지 않는다 — 머지는 사용자가 직접 실행한다.

- **스킬명:** `rehearsal`. 3스킬 플러그인 `rn-upgrade-kit`의 세 번째 — 나머지 둘은 `platform-watch`, `currency`(설계 완료).
- **위치:** `currency`가 "뭘로 올려야 하나"를 advisory로 산정한다면, 이 스킬은 그 권장 버전을 **실제로 돌려보는 실험실**이다. `platform-watch`·`currency`는 순수 advisory이고, 이 스킬만 게이트 통과 시 검증된 결과물을 브랜치로 넘긴다.

> **정정 이력:** §채택은 인터뷰 종료 후 추가됐다. 인터뷰는 "업그레이드를 실제 적용하는 기능은 만들지 않는다"를 확정 사항으로 물려받았으나, 이는 *별도 스킬 신설*에 대한 반대가 비목표로 과잉 일반화된 것이었다. 플러그인의 최종 목표에는 검증된 업그레이드의 실제 반영이 포함된다. 인터뷰 본문(라운드 1~7)과 그 결론은 모두 유효하며, 채택은 라운드 4(worktree 항상 폐기)와 충돌하지 않는다 — worktree는 여전히 폐기되고 커밋만 살아남는다.

## 스킬 표면 — frontmatter · 인자 문법 (인터뷰 후 추가 — 2026-08-09)

인터뷰는 이 스킬의 frontmatter를 다루지 않았다. 자매 스킬 둘은 `allowed-tools`를 확정했는데 이 스펙만 비어 있어 구현자가 지어내게 되는 상태였다.

```yaml
name: rehearsal
description: 격리된 git worktree에서 지정한 RN 버전 세트로의 업그레이드를 실제로 실행하고, 티어별 통과·실패·미실행 판정과 재현 커맨드를 담은 리포트를 낸 뒤 worktree를 폐기한다. 모든 게이트 통과 시에만 전용 브랜치로 채택을 제안한다. "RN 업그레이드 리허설", "업그레이드 시험", "rehearsal"에 사용. macOS·Linux 전용 — Windows에서는 실행을 거부한다.
user-invocable: true
argument-hint: <pkg@ver>... [--platform android|ios]
allowed-tools: Read Write Glob Bash WebFetch
```

- **`Bash` 필수** — 이 스킬의 존재 이유가 네이티브 빌드 실제 실행이다. 자매 스킬의 셸 제약은 여기 적용되지 않는다(§호스트 지원 매트릭스의 비대칭이 정확히 이 차이에서 나온다).
- **`WebFetch` 필요** — §인자 검증 검사 1(`registry`에 존재하는 버전인가)·2(프리릴리즈 아닌가)가 registry 조회다. 인터뷰 후 추가된 검사인데 도구가 명시되지 않았었다. `currency`와 같은 엔드포인트를 쓴다: `registry.npmjs.org/<pkg>/<ver>` (200이면 존재, 404면 부재) + `/-/package/<pkg>/dist-tags`.
- **`Agent` 불포함** — 티어는 순차 실행이고 판정은 메인 몫이다. 위임 이득이 없다.
- **`WebSearch` 불포함** — 조회 대상이 registry뿐이다.

> **구현 정정 (2026-08-18):** **검사 1의 registry 조회는 `WebFetch`가 아니라 `Bash`의 `node -e`다.** 위 `WebFetch` 줄은 실행 거부 판정을 요약 채널에 걸어둔 상태였다 — 근거는 §구현 감사 반영 «인자 검증 1을 `node -e`로». 검사 2는 인자 문자열만 보므로 조회가 필요 없다(위 줄이 검사 2를 조회로 묶은 것도 틀렸다). **`allowed-tools` 줄 자체는 이 정정으로 바꾸지 않는다** — 도구 목록 조정은 별도 판단이고, 스펙이 앞질러 정하면 구현과 또 어긋난다.

### 인자 문법

- **위치 인자 = 목표 버전 세트.** `<pkg>@<ver>` 형태를 1개 이상. `currency` 리포트의 커맨드 블록을 그대로 복붙한 형태가 정본이다.

## 티어 모델 (라운드 6에서 재정의됨)

원안의 4티어 중 T4(iOS)는 **독립 티어에서 폐기**되고 T2의 플랫폼 축으로 접힌다. 이유: Windows 미지원 확정 이후 남은 호스트 축이 macOS(전체) / Linux(Android만) 둘뿐이라, iOS는 "더 깊은 단계"가 아니라 "다른 플랫폼"이다.

| 티어                | 내용                                                                    | 플랫폼 축              |
| ------------------- | ----------------------------------------------------------------------- | ---------------------- |
| **T1**              | worktree 생성 → PM 감지 → 의존성 설치 → 패치 재적용 → 타입체크 → 테스트 | 없음 (공통)            |
| **T2/android**      | Gradle 빌드 → 에뮬레이터/기기 설치 → 부팅 → 로그 스캔                   | android                |
| **T2/ios**          | `pod install` → `xcodebuild` → 시뮬레이터 부팅 → 로그 스캔              | ios (macOS 호스트만)   |
| **T3/\<platform\>** | 스크린샷 수집 — **증거물 전용, 판정 근거 아님**                         | 부팅 성공한 플랫폼마다 |

### fail-fast 적용 범위

- **수직(티어 간)에만 적용한다.** T1 실패 → 모든 T2·T3 미실행. T2/android 실패 → T3/android 미실행.
- **수평(플랫폼 간)에는 적용하지 않는다.** `T2/android` 실패가 `T2/ios`를 막지 않는다.
- 실행 **순서**는 싼 것부터(android → ios). 순서는 출력 편의일 뿐 **게이트가 아니다**. 순서 ≠ 의존.

### 플랫폼 스코프 인자

- `--platform android|ios` — **좁히기 전용**. 기본값은 항상 "호스트가 허용하는 플랫폼 전부"다.
- **넓히는 방향의 인자는 두지 않는다.** 기본값이 항상 가장 안전한(=가장 많이 검증하는) 쪽에 선다.
- 인자로 제외된 플랫폼은 리포트에서 조용히 빠지지 않고 `미실행 (사용자 지정 스코프)`로 명시된다.

## 인자 검증 (인터뷰 후 추가 — `currency` 라운드 6)

목표 버전 세트는 **인자로만** 들어온다. 어떤 티어도 시작하기 전에 검증한다.

### 검사 3종

| # | 검사 | 검사 수단 | 실패 시 출력 |
| - | ---- | -------- | ------------ |
| 1 | 각 인자가 registry에 **존재하는 버전**인가 | `Bash`의 `node -e`로 상태 코드를 직접 읽는다 | `실행 거부 — 존재하지 않는 버전: <pkg>@<ver>` |
| 2 | **프리릴리즈가 아닌가** (`-rc`·`-beta`·`-next`·`-canary`) | 인자 문자열만 본다 — 조회 없음 | `실행 거부 — 프리릴리즈: <pkg>@<ver>` |
| 3 | **lockstep 짝이 전부 왔나** | 세트 목록은 `shared/lockstep-sets.md`를 Read해서 쓴다 — 본문에 나열하지 않는다 | `실행 거부 — lockstep 짝 누락: <빠진 패키지>` |

- **판정 아니라 실행 거부다.** Windows 거부와 같은 계열 — 티어가 시작되지 않았으므로 `실패`가 아니고, **리포트 파일도 생성하지 않는다.** 판정 어휘 3값은 그대로 유지된다.
- **검사 1·3은 조회·Read가 실패했을 때 거부하지 않는다.** 각각 `미실행`으로 두고 리포트 헤더에 사유를 적은 뒤 진행한다(§구현 감사 반영 «degrade — 4경로»). **확인 못 한 것을 위반으로 취급하지 않는다** — 거짓 부재로 실행을 막으면 사용자에게 우회 수단이 없다.
- **검사 3의 세트를 본문에 박지 않는 이유**는 `currency` 게이트 6과 **같은 목록을 봐야** 하기 때문이다. 양쪽에 각각 적으면 한쪽만 늘어나고, 그러면 `currency`가 권장한 세트를 이 스킬이 "짝 누락"으로 거부한다. 잠정 lockstep 후보(그 파일의 감지 규칙)로는 **거부하지 않는다** — 휴리스틱으로 손으로 친 인자를 막으면 우회할 방법이 없다.
- **인자 3종 외에 `실행 거부` 사유가 하나 더 있다: 업그레이드 표면의 dirty tree.** 인자가 아니라 트리 상태이므로 위 번호를 밀지 않는다(`shared/lockstep-sets.md`가 `인자 검증 3`을 이름으로 참조한다). 규칙과 근거는 §구현 감사 반영 «`base_sha` 정의»·«dirty tree 처리».
- **전달 방식과 무관하게 필요하다.** `currency`가 커맨드 블록을 출력하든 사용자가 손으로 치든 인자는 사람 손을 거쳐 들어온다. 파일 핸드오프가 없어서 생긴 비용이 아니다.
- 짝 하나만 올리는 리허설은 **무의미하다** — `currency` §게이트 6의 *"짝 하나가 걸리면 세트 전체가 걸린 것"*과 같은 이유다. 반쯤 맞춘 세트로 T2까지 돌면 그 관측이 무엇을 뜻하는지 아무도 모른다.

### 산정 시각 주석

`currency` 리포트의 커맨드 블록에는 `# 산정 시각: YYYY-MM-DD` 주석이 붙는다. 그대로 복붙하면 함께 온다.

- 주석이 오면 **실행 전에 경과일을 경고한다.** 거부가 아니라 경고다 — 낡은 타깃도 리허설 자체는 유효하다. 경고 임계일은 `shared/constants.md`의 `target_staleness_warn_days`(기본 14)다 — 인터뷰는 "오래됐으면"이라고만 정했고 값이 없었다. 14일 근거: `currency` 게이트 3의 minor soak와 같은 값이다. **권장 버전이 한 soak 주기만큼 묵었으면 그 사이에 새 stable이 나왔을 수 있다.**
- 리포트 헤더에도 남긴다: `타깃 산정: 2026-08-09 (21일 경과)`.
- **주석이 없으면 경고하지 않는다** (손으로 친 경우). 없는 것을 실패로 만들지 않는다.
- 근거: 파일 핸드오프가 없으므로 낡음을 알 길이 이 주석뿐이다. `currency`는 자기 권장 버전의 신선도를 판정할 주체가 아니다 — 권장 버전은 soak·churn 게이트 산물이라 마감일보다 훨씬 빨리 썩고, 판정 책임이 소비자인 이 스킬로 넘어온다.

### `currency` 리포트를 파싱하지 않는다

- 사람용 리포트를 기계 스키마로 겸용하면 **리포트 문구 개선이 이 스킬의 회귀**가 된다. 잘못된 결합 방향이다.
- §Technical Context에 열려 있던 *"미지정 시 `currency` 리포트에서 읽는 경로를 열어둘 수 있다(설계 재량)"*는 **닫혔다.**
- 인자가 없으면 실행 거부다. 타깃을 추측하지 않는다.

## T1 — 상세

### 패키지 매니저 감지 (기계적)

lockfile 기반 1회 감지. 4종 전부 지원.

| lockfile                 | PM   | 설치                             | 패치 메커니즘 (우선순위)                             |
| ------------------------ | ---- | -------------------------------- | ---------------------------------------------------- |
| `pnpm-lock.yaml`         | pnpm | `pnpm install --frozen-lockfile` | `patches/` + `patchedDependencies` → `patch-package` |
| `package-lock.json`      | npm  | `npm ci`                         | `patch-package` (postinstall)                        |
| `yarn.lock`              | yarn | `yarn install --immutable`       | `.yarn/patches` + resolutions → `patch-package`      |
| `bun.lock` / `bun.lockb` | bun  | `bun install --frozen-lockfile`  | `patches/` + `patchedDependencies` → `patch-package` |

- **PM 네이티브 메커니즘 우선.** `patches/` + `patch-package`는 폴백.
- lockfile이 둘 이상이면 실행 거부 사유가 아니라 T1 실패로 처리하고 사유를 명시한다("PM 판별 불가: lockfile 2종 존재").

### 패치 재적용 실패 처리

1. hunk 실패 발생 → 실행에 `[패치 불완전]` 플래그 부착
2. **붙은 패치만 적용된 상태로 T1 나머지(타입체크·테스트)를 계속 진행** — 정보 수집
3. T1 판정 = **실패**, T2 이후 `미실행 (패치 불완전으로 중단)`
4. 리포트에 실패한 패치의 대상 패키지·hunk 번호를 명시

### 베이스라인 — 조건부 대조군

**통과 시 비용 0. 실패했을 때만 지불한다.**

1. 업그레이드 적용 후 T1을 먼저 돌린다.
2. 타입체크 또는 테스트가 실패하면 **그때만** 같은 worktree를 업그레이드 전 상태로 되돌려 재측정한다.
3. 판정은 **델타**로 서술한다: "신규 에러 N개 / 기존 부채 M개".
4. 신규 에러 0이면 T1은 **통과**다 — 기존 부채는 업그레이드 산물이 아니다.

> 이 절이 없으면 이미 깨져 있는 레포에서 T1은 영원히 실패로 나오고 스킬 전체가 쓸모없어진다. 픽셀 diff를 금지한 이유(거짓 양성 제거)와 정확히 같은 논리다.

### 캐시 전략

worktree는 매번 신규 생성되므로 `node_modules`·`Pods`는 매번 새로 깔린다. **worktree 내부에 캐시를 남기지 않는다.**

- 유일한 캐시 의존은 **호스트 전역 store**: pnpm store / yarn cache / npm cache / `~/.gradle` / CocoaPods 캐시.
- worktree 재사용·`node_modules` 복사·하드링크 주입은 **하지 않는다** — stale 산물이 만드는 거짓 통과가 이 스킬이 가장 싫어하는 실패 모드다.

## T2 — 부팅 판정선

**판정선: 첫 프레임 렌더 + 생존 + 로그 클린 — 아래 통과 조건 3개가 관측하는 것까지다.** 인증 이후 화면은 **비범위**다.

> **정정 (2026-08-29):** 원안(인터뷰 라운드 1)의 판정선은 *"첫 프레임 렌더 + 로그인 화면 도달"*이었다. 그런데 아래 통과 조건 어느 것도 **그려진 화면의 정체**를 관측하지 않는다 — 첫 프레임은 온보딩·에러 화면에서도 나온다. 관측 수단 없는 문구를 통과 정의에 실으면 통과 문구 자체가 환각 금지 위반이 된다("관측 안 한 것을 사실로 적지 않는다"). 로그인 화면 관측 수단을 새로 만드는 쪽은 기각 — 화면 정체 판정은 앱별 화면 구조에 물리는 순간 *"리허설 룸은 앱 비밀을 몰라야 한다"*(아래 절)와 충돌 경로가 생긴다. **판정선을 관측 가능한 것까지로 내리고, 화면 정체 미관측을 리포트 한계 문구에 명시한다.** 인터뷰 기록(§인터뷰 라운드 1·§가정 도전 표)은 이력이므로 고치지 않는다.

### 통과 조건 (전부 충족)

1. 앱 프로세스가 N초(기본 60s) 생존
2. **첫 프레임 렌더 신호 관측** (RN 브리지/Fabric 마운트 완료 — Choreographer / `ReactNativeJS` 초기화 로그 또는 `dumpsys gfxinfo` 프레임 카운트 > 0)
3. 로그 스캔 클린 — `FATAL EXCEPTION` 0건, `ReactNativeJS` Error 0건, ANR 0건

> **구현 정정 (2026-08-18):** 위 1번의 `boot_survival_seconds`는 **통과 조건이지 상한이 아니다.** 원안은 어느 단계에도 상한을 두지 않아 Gradle 빌드·`pod install`·에뮬레이터 부팅이 걸리면 스킬이 무한정 멈추는 상태였다. **단계 타임아웃 4종이 신설됐고 초과는 `실패 (타임아웃 <상수명>)`다** — 미실행이 아니다. 값·근거는 §구현 감사 반영 «단계 타임아웃 4종».

### 인증은 스킬 책임이 아니다 (명시적 비목표)

- 테스트 계정 크리덴셜·토큰·스토리지 스냅샷 주입·자동 로그인 스크립트 — **전부 만들지 않는다.**
- 근거: 인증을 스킬 안으로 끌어들이는 순간 스킬이 앱별 비밀에 물린다. 리허설 룸은 앱 비밀을 몰라야 한다.
- 리포트는 이 한계를 명시한다: `T2 통과 = 첫 프레임 렌더 + 생존 + 로그 클린. 어느 화면까지 갔는지는 관측하지 않는다 — 인증 이후는 미검증(비범위).` (2026-08-29 정정 — 위 판정선 정정과 같은 사유. 구 문구 *"로그인 화면까지 도달"*은 관측 안 한 것을 주장했다.)

## T3 — 증거물

- 스크린샷은 **증거물 전용.** 판정에 절대 쓰지 않는다.
- **픽셀 diff 판정 금지.** 지도 타일·애니메이션 프레임·폰트 렌더링 차이가 거짓 양성을 양산한다.
- 부팅에 성공한 플랫폼마다 수집. android만 부팅됐으면 `T3/android`만 존재하고 `T3/ios`는 미실행.
- **수집 커맨드·장수·시점은 못박혀 있다** — `adb exec-out screencap` / `xcrun simctl io booted screenshot`, 플랫폼당 1장, `boot_survival_seconds` 생존 확인 직후. 커맨드가 정의돼 있지 않으면 재현 블록에 실을 줄을 작문하게 되고, 그건 환각 금지 위반이다. 상세는 §구현 감사 반영 «T3 스크린샷 수집 방법».
- **수집 실패는 T3를 실패로 만들지 않는다.** `미실행 (스크린샷 수집 실패: <사유>)`로 남긴다 — 스크린샷은 판정에 절대 쓰이지 않으므로(위) 그 부재는 업그레이드에 대한 관측이 아니다. 이미 난 T2 판정도 바뀌지 않는다.

## worktree 수명 + 산출물

### 수명

**매번 신규 생성 → 항상 즉시 폐기.** 실패해도 보존하지 않는다.

- 생성 경로는 `shared/constants.md`의 `worktree_path_template`에서 온다. **스킬 본문에도 리포트에도 경로를 직접 적지 않는다** — 같은 경로가 재현 블록·수동 정리 커맨드·충돌 판정 **세 곳에 동시에** 박히므로, 한 곳만 고치면 나머지 둘이 조용히 거짓이 된다. 근거는 §구현 감사 반영 «worktree 경로 상수화».
- 폐기 전에 진단 증거(빌드 로그·logcat·tsc 출력·테스트 출력·스크린샷)를 worktree 밖 `artifacts/`로 복사한다.
- 디스크 누적 0, 상태 오염 0. 사용자는 트리에 들어가 손보는 대신 **재현 커맨드 시퀀스**로 되살린다.

### 폐기 실패

**조용히 넘기지 않는다.** POSIX에서도 Gradle 데몬 잔존 등으로 실패할 수 있다.

- 실패 시 리포트에 명시 + **수동 정리 커맨드 제공** (`git worktree remove --force <path>`, `git worktree prune`).
- 조용히 넘기면 "항상 폐기"라는 계약이 거짓말이 되고 누적 문제가 그대로 돌아온다.
- **이 상태를 다음 실행이 마주쳤을 때의 처리**(고아 디렉토리는 prune 후 삭제 + 헤더 표기 / `git worktree list`에 등록돼 있으면 실행 거부)는 §구현 감사 반영 «기존 디렉토리 처리»에 있다. 원안은 폐기 실패만 정의하고 **그 다음 실행이 무엇을 보게 되는지를 비워뒀다.**

### `<target>` — 실행 식별자 (인터뷰 후 추가 — 2026-08-09)

리포트 파일명·artifacts 디렉터리·채택 브랜치명이 전부 `<target>`을 쓰는데 **정의가 없었다.** 인자는 lockstep 세트라 패키지가 여럿이다.

| 조건 | `<target>` |
| --- | --- |
| 세트에 `react-native`가 있음 | 그 버전 (`0.83.4`) |
| 없음 | 세트를 패키지명 사전순 정렬한 첫 항목의 `<pkg>-<ver>` (경로 안전하게 `@`·`/`를 `-`로) |

- **RN 우선 근거:** RN은 lockstep 반경이 가장 넓고(`currency` §게이트 6) 리허설의 사실상 주어다. 사람이 리포트 목록을 훑을 때 찾는 것도 RN 버전이다.
- 전체 세트는 리포트 헤더와 채택 커밋 메시지에 **전부** 실린다. `<target>`은 **식별자일 뿐 내용이 아니다.**

### 같은 날 · 같은 타깃 재실행 — 덮어쓰기

리포트 파일과 artifacts 디렉터리 **둘 다 덮어쓴다.** 시각 suffix를 붙이지 않는다.

- 자매 스킬 둘이 같은 규칙으로 닫혔고(`platform-watch`·`currency` 라운드 9c), 근거도 같다 — suffix를 붙이면 보존 상한 계산이 "N개 실행"이 아니라 "N개 파일"로 흔들린다.
- 덮어쓰기 전에 **직전 artifacts를 지운다.** 두 실행의 로그가 한 디렉터리에 섞이면 어느 실행의 증거인지 못 가린다 — 리포트가 인용하는 경로가 거짓이 된다.

### artifacts 보존 상한

실행당 전체 빌드 로그 + logcat + 스크린샷은 수십 MB다. **무제한이면 결국 누적된다.**

- 실행마다 날짜 디렉터리: `artifacts/YYYY-MM-DD-<target>/`
- **최근 N개만 보존, 초과분 자동 정리.** N은 `shared/constants.md`의 `artifact_retention_n`(기본 3)에서 온다 — 스킬 본문에 하드코딩하지 않는다. 정리한 개수를 리포트 말미에 한 줄로 보고한다.
- **자동 정리는 세 스킬 중 이 스킬만 한다.** 자매 두 스킬(`platform-watch`·`currency`)은 같은 자리에서 수동 정리 커맨드만 내는데, 그 둘에는 파일 삭제 수단이 없기 때문이다(`Write`는 덮어쓰기만 하고 `currency`의 `Bash`는 `node -e` 한 용도로 못박혀 있다). 이 스킬은 `Bash`에 용도 제한이 없으므로 실제로 지우고 지운 개수를 보고할 수 있다 — **세 스킬이 달라지는 게 맞다. 도구가 다르다.** 이 한 줄이 없으면 나중에 "왜 여기만 다르지"가 드리프트로 오인된다.
- 부팅 생존 대기 시간(`boot_survival_seconds`, 기본 60)과 산정 시각 경고 임계일(`target_staleness_warn_days`, 기본 14)도 같은 파일에서 온다. **worktree 경로 템플릿과 단계 타임아웃 4종도 같은 파일에서 온다** — `worktree_path_template`·`step_timeout_{install,check,build,boot}_seconds`.

### 쓰기 범위 (확정 항목의 정제)

원안 "산출물은 리포트 파일 하나뿐"은 다음으로 정제된다:

- **사용자 작업 트리의 소스·`package.json`·네이티브 설정 수정 금지** — 그대로 유지. 예외 없음. worktree 내부 수정은 격리 공간이므로 이 금지 대상이 아니다.
- **쓰기는 셋:** 리포트 파일 1개 + 상한 있는 `artifacts/` 증거 디렉터리 + (채택 시에만) 전용 브랜치 커밋 1개.
- `.gitignore`도 **수정하지 않는다** (설정 파일이다). 출력 디렉터리를 무시하도록 README에서 사용자에게 안내한다.

## 채택 (adopt)

리허설이 검증한 결과물을 버리지 않고 전용 브랜치로 남기는 **종단 옵션**. 별도 스킬이 아니다 — 게이트가 리허설 자신의 판정에 달려 있고 산출물도 리허설의 worktree라서, 분리하면 신뢰 근거를 처음부터 다시 만들어야 한다.

### 핵심: 새 변경 엔진이 아니라 "안 버리는 것"

모든 티어를 통과한 시점에 worktree 안에는 이미 검증된 업그레이드 결과물이 있다. 채택은 그것을 커밋할 뿐이다.

```
worktree 안에서 커밋  →  worktree 폐기  →  브랜치만 살아남음
```

**라운드 4의 "항상 폐기"는 그대로 지켜진다.** worktree는 성공·실패·채택 여부와 무관하게 매번 폐기되고, 채택한 경우 커밋만 남는다.

### 채택 게이트 (전부 만족해야 함)

1. 실행된 모든 티어가 `통과` — `실패`가 하나도 없을 것
2. `[패치 불완전]` 오염 플래그 없음
3. 조건부 베이스라인이 **측정되지 않았을 것** — 즉 업그레이드 후 타입체크·테스트가 처음부터 깨끗했을 것. 베이스라인이 돌았다는 건 검사가 한 번 실패했고 그게 `기존 부채`로 설명됐다는 뜻이다. 그 실행의 T1은 통과지만 **"기존 부채와 업그레이드 산물이 같은 파일에서 겹치지 않는다"는 보증은 없다** — 게이트 1로는 안 걸리므로 별도 게이트가 필요하다
4. 사용자 명시 확인

**하나라도 어긋나면 채택 옵션을 제시조차 하지 않는다.** "통과했지만 조건부"인 상태에서 적용을 권하면 이 스킬이 지켜온 _"통과 ≠ 안전"_ 이 무너진다.

`미실행`은 게이트를 막지 않되(호스트 제약·사용자 스코프는 실패가 아니다) 확인 문구에 **무엇이 검증되지 않았는지 명시**한다.

**게이트 3은 사후 감사 근거를 남긴다.** `베이스라인: 미측정` 또는 `베이스라인: 측정됨 (<사유>)`을 리포트 헤더에 **채택 여부와 무관하게 항상** 싣고, 채택한 실행은 **커밋 메시지에도** 싣는다. 원안은 이 필드를 어디에도 두지 않아 채택 후 브랜치만 남으면 게이트 3 통과 근거를 확인할 방법이 없었다 — **검증 못 하는 게이트는 게이트가 아니다.** 근거는 §구현 감사 반영 «베이스라인 필드».

### 채택 범위

리허설이 **실제로 검증한 것**만 실린다 — 의존성 버전, lockfile, 네이티브 설정.

**재현 불가능한 수작업이 섞였으면 채택 불가**다. 패치 재생성(`[패치 불완전]`)이나 breaking API 코드 마이그레이션이 필요했던 실행은 게이트 2·1에서 이미 걸러진다.

### 금지

- **자동 머지·자동 push** — 어떤 조건에서도
- **사용자 현재 브랜치에 직접 커밋**
- **채택 브랜치의 rebase·`--onto`** — 검증 기준점을 옮기는 어떤 조작도 금지
- 확인 없는 채택 (기본값은 항상 미채택)
- **기존 브랜치 덮어쓰기·force update** — 아래

### 브랜치 이름 충돌 (인터뷰 후 추가 — 2026-08-09)

`rn-upgrade/<target>-<base_sha>`는 같은 타깃을 같은 base에서 두 번 채택하면 충돌한다.

- **충돌 시 채택하지 않는다.** `채택 안 함 (동일 브랜치 존재: <이름>)`으로 리포트에 남기고 사용자가 기존 브랜치를 확인·삭제하게 한다.
- `-f`·`--force`·suffix 자동 부여 **전부 금지**. 브랜치명이 곧 "이 커밋 위에서 이 타깃을 검증했다"는 주장이므로, 같은 이름에 다른 내용을 넣으면 **주장과 내용이 어긋난다** — rebase를 금지한 이유와 같은 계열이다.
- 리포트·artifacts는 덮어쓰지만 브랜치는 안 덮어쓴다. **비대칭이 의도적이다** — 앞의 둘은 이 실행의 관측이고 브랜치는 사용자가 머지할 수도 있는 산물이다.

### base 신선도 — 게이트가 막지 못하는 누수

worktree는 `base_sha`에서 생성되고 검증은 **그 커밋 위에서** 이뤄진다. 리허설은 빌드+부팅까지 수십 분이 걸리고, 그동안 사용자는 작업 브랜치를 계속 진행한다. 따라서 **머지 시점의 트리는 검증된 트리가 아니다.**

게이트 4개로는 이걸 못 막는다 — *"통과 ≠ 안전"*이 정확히 이 지점으로 샌다. 막는 대신 **드러낸다.**

1. `base_sha`를 **브랜치명과 리포트 양쪽에 박는다** (`rn-upgrade/0.86.2-a3f9c21`). 브랜치만 봐도 어느 커밋 위에서 검증됐는지 알 수 있어야 한다.
2. 머지 커맨드를 단독으로 주지 않는다. **선행 확인 커맨드와 한 블록으로** 낸다.

```sh
# 검증 기준: a3f9c21
git log --oneline a3f9c21..HEAD   # 비어 있지 않으면 아래 경고 적용
git merge rn-upgrade/0.86.2-a3f9c21
```

3. 리포트 §채택에 고정 문구를 싣는다:

> 이 브랜치는 `<base_sha>` 위에서 검증됐다. 그 이후 커밋이 있으면 머지 결과는 검증된 트리가 아니다 — 재리허설을 권장한다.

4. **스킬은 rebase하지 않는다.** rebase하면 검증 결과가 무효가 되는데 브랜치는 여전히 "검증됨"을 주장하게 된다 — 최악의 조합이다. `--onto`·`--rebase` 계열 옵션을 두지 않는다.

### 산출

브랜치명(`base_sha` 포함) + 선행 확인 커맨드 + 머지 커맨드 + base 신선도 경고문을 리포트에 낸다. 실행은 사용자 몫이다.

> 위 예시의 `보존 3개`의 `3`은 값이 아니라 예시다 — 실제 보존 개수는 `shared/constants.md`의 `artifact_retention_n`에서 온다.

- **요약 한 줄을 플랫폼별로 분리한다.** 한 플랫폼 통과를 전체 통과로 접지 않는다.
- 실패 상세는 **발췌문**으로 인용한다(상위 N줄). 전체 로그는 `artifacts/`에 있고 경로만 적는다.
- **`검증 기준`과 `베이스라인`은 조건부가 아니다.** 앞은 "무엇을 검증했나"의 정의고, 뒤는 채택 게이트 3의 유일한 사후 감사 근거다. 조건부로 두면 줄이 없을 때가 "clean이라서 생략"인지 "안 봐서 생략"인지 구분되지 않는다. 작업 트리가 dirty면 `검증 기준: <base_sha> (작업 트리 dirty — 검증에 미포함: <경로 목록>)`로 적는다.
- **degrade의 흔적도 헤더 줄이다** — `인자 검증 1 미실행 (registry 조회 실패)` · `인자 검증 3 미실행 (lockstep 목록 도달 실패)` · `artifacts 쓰기 실패: <사유> — 전체 로그 없음` · `기존 worktree 디렉토리 삭제: <경로>`. 줄이 없으면 degrade가 없었다는 뜻이어야 한다 — **조용히 열화된 리허설은 정상 실행과 구분되지 않는다.**

### 재현 커맨드 시퀀스

**단일 복붙 블록 1개.** worktree는 이미 폐기됐으므로 **재현은 worktree 재생성부터** 시작한다.

1. **티어 경계는 블록 안 주석으로** 표시한다 (`# --- T1 ---`, `# --- T2/android ---`). 티어별 블록 분할의 유일한 실익을 파일·블록 증가 없이 흡수한다.
2. **블록은 실패한 티어에서 끝난다.** 미실행 티어의 커맨드는 넣지 않는다.
3. **커맨드는 새로 작문하지 않고 실제 실행된 것에서 그대로 추출한다.** 작문하면 스킬이 검증할 수 없는 커맨드를 리포트에 싣게 된다 — 환각 금지 원칙 위반이다.
4. **셸은 POSIX 고정.** 감지·분기 없음 (Windows 미지원의 직접 결과).
5. 블록 말미에 정리 커맨드(`git worktree remove --force …`)를 포함한다.
6. **채택한 실행이면 커밋·브랜치 생성 커맨드도 블록에 실린다** — 정리 커맨드 **앞**에. 채택은 재현 가능해야 한다. 채택하지 않은 실행에는 넣지 않는다(안 돌린 커맨드를 싣지 않는다는 3번의 연장).
7. **`timeout` 래퍼를 두르지 않는다.** 단계 상한은 스킬이 단계를 감싸 건 것이지 사용자가 친 커맨드의 일부가 아니다 — 두르면 3번(실행분 그대로 추출)이 깨진다. 대신 **타임아웃으로 끝난 단계에만** 그 줄 위에 `# 이 단계는 <상수명> 초과로 중단됐다` 주석 한 줄을 단다. 블록은 그 줄에서 끝난다(2번).
8. **worktree 경로는 `shared/constants.md`의 `worktree_path_template`에서 온다.** 블록에 인쇄된 경로를 정본으로 삼지 마라 — 재현 블록·수동 정리 커맨드·충돌 판정이 같은 값을 봐야 한다.

## Non-Goals (명시적 비목표)

- **자동 머지·자동 push·사용자 현재 브랜치 수정** — 채택은 전용 브랜치 커밋까지만이고 머지는 사용자가 직접 실행한다 (§채택). ~~업그레이드를 실제 적용하는 기능~~은 인터뷰 후 정정으로 비목표에서 제외됐다 — §Goal 정정 이력 참조.
- **게이트 미통과 상태의 채택** — 티어 실패·오염 플래그·`원래 깨져 있었음`이 하나라도 있으면 채택 옵션 자체를 제시하지 않는다.
- **사용자 작업 트리의 소스·`package.json`·네이티브 설정·`.gitignore` 수정**
- **인증 시딩·자동 로그인·크리덴셜 관리** — 앱별 비밀에 물리지 않는다.
- **픽셀 diff / 시각 회귀 판정** — 스크린샷은 증거물 전용.
- **CI 디스패치** — `gh workflow run`·폴링·리모트 push 전부 스킬 밖. README 문서로만 안내.
- **Windows 지원** — 실행 거부.
- **`currency` 리포트 파싱** — 목표 버전은 인자로만 받는다. 사람용 리포트를 기계 스키마로 겸용하지 않는다 (§인자 검증).
- **타깃 추측** — 인자가 없으면 실행 거부다. 최신·권장을 스스로 산정하지 않는다(`currency` 소관).
- **낡은 타깃 거부** — 산정 시각이 오래됐으면 경고만 한다. 낡은 타깃도 리허설 자체는 유효하다.
- **worktree 보존·재사용** — 실패해도 폐기.
- **성능 회귀·번들 사이즈·실기기 검증**
- **"안전하다"는 결론** — 스킬은 관측만 낸다.

## Acceptance Criteria

- [ ] Windows 호스트에서 실행 시 어떤 티어도 시작하지 않고 즉시 중단하며, **리포트 파일이 생성되지 않는다**
- [ ] 존재하지 않는 버전을 인자로 주면 어떤 티어도 시작하지 않고 실행 거부되며 리포트 파일이 생성되지 않는다 — **존재 확인은 `node -e` 상태 코드로 하며 `WebFetch`를 쓰는 코드 경로가 없다**
- [ ] `node -e` 조회 자체가 실패하면 **거부하지 않고** 인자 검증 1을 `미실행`으로 두고 진행하며, 리포트 헤더에 `인자 검증 1 미실행 (registry 조회 실패)`가 출력된다
- [ ] 프리릴리즈 버전(`-rc`·`-beta`·`-next`·`-canary`)을 인자로 주면 실행 거부된다 — 검사 1이 미실행이어도 이 판정은 그대로 난다(인자 문자열만 본다)
- [ ] lockstep 짝 중 하나만 인자로 주면 실행 거부되고 빠진 패키지명이 출력된다 — **세트 목록은 `shared/lockstep-sets.md`에서 오며 스펙·스킬 본문에 나열되지 않는다**
- [ ] `shared/lockstep-sets.md`에 도달하지 못하면 **거부하지 않고** 인자 검증 3을 `미실행`으로 두고 헤더에 사유가 출력된다
- [ ] 잠정 lockstep 후보(감지 규칙 산물)로는 실행이 거부되지 않는다 — 거부는 확정 세트로만
- [ ] 인자 검증 실패가 `실패` 판정이 아니라 실행 거부로 처리된다 (판정 어휘 3값 불변 검증)
- [ ] `# 산정 시각` 주석이 있으면 경과일이 리포트 헤더에 출력되고, 주석이 없으면 경고가 출력되지 않는다
- [ ] 산정 시각이 오래됐어도 실행이 거부되지 않는다 (경고만)
- [ ] `currency` 리포트를 읽는 코드 경로가 존재하지 않으며, 인자 미지정 시 타깃을 추측하지 않고 실행 거부한다
- [ ] Linux 호스트에서 `T2/ios`가 `미실행 (macOS 필요)`로, `--platform android` 지정 시 `T2/ios`가 `미실행 (사용자 지정 스코프)`로 — **서로 다른 문구**로 출력된다
- [ ] `--platform`이 기본 스코프를 넓히는 방향으로는 동작하지 않는다 (넓히기 인자 부재 검증)
- [ ] `T2/android` 실패 시에도 `T2/ios`가 실행된다 (수평 fail-fast 부재 검증)
- [ ] `T1` 실패 시 모든 `T2`·`T3`가 `미실행 (앞 티어 실패)`로 출력된다 (수직 fail-fast 검증)
- [ ] 기존 타입 에러가 있는 레포에서 업그레이드가 새 에러를 만들지 않으면 `T1 — 통과`가 나온다 (조건부 베이스라인 검증)
- [ ] T1 통과 시 베이스라인 재측정이 **실행되지 않는다** (조건부 비용 0 검증)
- [ ] 패치 hunk 실패 시 `T1 — 실패` + 실행 전체에 `[패치 불완전]` 플래그 + tsc/test 관측이 **버려지지 않고** 플래그 달려 실린다
- [ ] 판정 어휘가 `통과`·`실패`·`미실행` 3값을 벗어나지 않는다 (`개입 필요` 같은 4번째 어휘 부재 검증)
- [ ] 모든 리포트에 "통과 ≠ 안전" 고정 문구가 존재한다
- [ ] pnpm·npm·yarn·bun 4종 lockfile 각각에서 PM과 패치 메커니즘이 올바르게 감지된다
- [ ] 실행 종료 후 worktree가 존재하지 않는다 (성공·실패 무관)
- [ ] worktree 폐기 실패 시 리포트에 명시되고 수동 정리 커맨드가 제공된다
- [ ] `artifacts/`가 최근 N개(기본 3)를 초과하면 자동 정리되고 정리 개수가 리포트에 보고된다
- [ ] 재현 블록이 POSIX 단일 블록이고, 티어 경계 주석을 포함하며, **실패한 티어에서 끝난다**
- [ ] 재현 블록의 커맨드가 실제 실행 로그에서 추출된 것과 문자열 일치한다 (작문 부재 검증)
- [ ] 실행 후 `git status`가 사용자 작업 브랜치에서 clean이다 (소스·설정 미수정 검증)
- [ ] 스크린샷 비교·픽셀 diff 코드 경로가 존재하지 않는다
- [ ] 티어 하나라도 `실패`면 채택 옵션이 제시되지 않는다 (게이트 1 검증)
- [ ] `[패치 불완전]` 플래그가 있으면 전 티어 통과여도 채택 옵션이 제시되지 않는다 (게이트 2 검증)
- [ ] 베이스라인이 `원래 깨져 있었음`이면 채택 옵션이 제시되지 않는다 (게이트 3 검증)
- [ ] 게이트 충족 시에도 사용자 확인 없이는 채택되지 않는다 — 기본값 미채택 (게이트 4 검증)
- [ ] `미실행` 티어가 있어도 게이트는 막히지 않되, 확인 문구에 미검증 항목이 명시된다
- [ ] 채택 후에도 worktree가 존재하지 않는다 — 커밋만 남는다 (라운드 4 불변 검증)
- [ ] 채택은 전용 브랜치 커밋까지만 수행하며 머지·push·사용자 현재 브랜치 체크아웃을 하지 않는다
- [ ] 채택 시 리포트에 브랜치명과 사용자가 실행할 머지 커맨드가 출력된다
- [ ] 채택 브랜치명에 `base_sha`가 포함된다 — 같은 타깃을 두 번 채택해도 브랜치가 충돌하지 않는다
- [ ] 머지 커맨드가 단독으로 출력되지 않고 `git log <base_sha>..HEAD` 선행 확인 커맨드와 한 블록으로 나온다
- [ ] 채택 리포트에 base 신선도 경고문이 항상 존재한다 (base가 최신이어도 출력)
- [ ] rebase·`--onto` 코드 경로가 존재하지 않는다 (검증 기준점 이동 금지 검증)

## Assumptions Exposed & Resolved

| 가정 | 도전 | 결론 |
|---|---|---|
| "부팅 성공"은 자명하다 | 로그인 필요 앱은 인증 없이 실제 화면에 못 들어간다 | 판정선 = 첫 프레임 + 로그인 화면 도달. 인증 이후 비범위 |
| T4(iOS)는 위임할지 말지의 문제다 | 호스트가 win32면 로컬 경로가 영원히 없다 | 호스트 능력 분기. 이후 Windows 배제로 T4가 `T2/ios`로 접힘 |
| 업그레이드 후 T1 실패 = 업그레이드가 깼다 | 이미 깨진 레포면 항상 실패로 나온다 | 조건부 대조군. 판정은 델타(신규 에러 N개) |
| worktree는 매번 만들고 버려야 한다 (컨트래리언) | 고정 경로 재사용하면 캐시·보존 딜레마가 동시에 증발한다 | 재사용 기각 — stale 산물의 거짓 통과가 더 나쁘다. 대신 증거만 밖으로 복사 |
| 산출물은 리포트 파일 하나뿐 | 실패 진단 증거를 어디에 두나 | 리포트 1개 + 상한 있는 `artifacts/`로 정제. 소스 미수정은 불변 |
| 패치 실패는 3값에 안 들어간다 → 4번째 어휘 필요 | 어휘를 늘리면 "안전/깨짐 2값 금지" 정신이 다른 방향으로 무너진다 | 4번째 어휘 대신 **오염 플래그**. 3값 유지 |
| 재현 시퀀스는 셸을 감지해 분기해야 한다 (심플리파이어) | 검증 못 하는 실행 경로를 지원한다고 쓰는 게 문제의 뿌리다 | Windows 배제 → POSIX 고정, 분기 로직 전부 삭제 |
| fail-fast는 확정 규칙이니 전역 적용된다 | 플랫폼 축이 생기면 android/ios는 앞뒤가 아니다 | fail-fast는 **수직에만**. 수평은 독립. 순서 ≠ 의존 |
| 게이트 4개를 통과한 채택 브랜치는 머지해도 검증된 상태다 | 검증은 `base_sha` 위에서 이뤄졌고, 리허설이 도는 수십 분간 사용자 브랜치는 전진한다 — 머지 시점 트리는 검증된 트리가 아니다 | 막지 않고 **드러낸다**. `base_sha`를 브랜치명·리포트에 박고, 머지 커맨드에 선행 확인을 묶고, 신선도 경고를 고정 출력. rebase는 금지(검증 무효화 + 검증됨 주장 = 최악) |
| 업그레이드를 실제 적용하는 기능은 만들지 않는다 (인터뷰 후 정정) | 그 금지가 지키려던 불변식은 둘 — ①사용자 브랜치 미수정 ②검증 안 된 걸 통과로 팔지 않기. 전용 브랜치 커밋은 둘 다 안 건드린다 | 비목표를 **자동 머지·자동 push·현재 브랜치 수정**으로 좁힘. 게이트 4개를 통과한 실행에 한해 §채택 허용 |

## Technical Context

- 자매 스킬 정본: `seed/rn-currency-SKILL.md` — frontmatter(`name`/`description`/`user-invocable`/`argument-hint`/`allowed-tools`), 번호 절 구조, 서두 불릿 원칙, `references/*.md` 지연 로드 패턴을 그대로 따른다.
- `currency`가 산정하는 **권장 버전(safe target)**이 이 스킬의 자연스러운 입력이다. 전달은 파일이 아니라 `currency` 리포트의 **복사 가능한 단일 커맨드 블록**이고 사용자가 전송체다(`.rn-upgrade-kit/handoff/` 아래 currency 소유 파일은 없다). **목표 버전은 인자로만 받는다 — `currency` 리포트를 파싱하지 않는다** (§인자 검증). ~~미지정 시 리포트에서 읽는 경로를 열어둘 수 있다(설계 재량)~~는 `currency` 라운드 6에서 기각됐다.
- 대상 프로젝트 전제: New Architecture (`newArchEnabled=true`, Hermes, Nitro Modules, Reanimated 4), **Expo 미사용**.

## 구현 감사 반영 — 2026-08-18

`docs/audit-2026-08-12.md`의 지적 8건(#2·#5·#6·#9·#10·#11·#12·#13·#14)을 구현이 닫으면서 이 스펙의 결정이 바뀐 것들이다. 위 본문의 해당 자리에도 «구현 정정» 인용문으로 표시해 뒀다.

- **«`base_sha` 정의»** — `base_sha`는 **실행 시작 시점의 현재 브랜치 HEAD**이고 `git rev-parse HEAD` **1회**로 고정한다. 인자로 받지 않는다: 이 플러그인의 인자는 좁히기 전용이라 base를 인자로 열면 넓히는 인자가 된다. 근거는 스펙이 `base_sha`를 **쓰기만 하고 정의하지 않았다**는 것이다 — `git worktree add <path> a3f9c21`의 `a3f9c21`이 어디서 오는지가 어디에도 없었다. **1회 고정인 이유**는 worktree 경로·브랜치명·리포트 헤더·머지 선행 확인 **네 곳이 같은 값을 봐야** 하기 때문이다. 도중에 다시 읽으면 넷이 서로 다른 커밋을 가리킬 수 있고, 그러면 브랜치명이 주장하는 검증 기준과 실제 검증 기준이 어긋난다.

- **«dirty tree 처리»** — **업그레이드 표면**(`package.json` · lockfile · `android/**` · `ios/**` · `patches/**`)에 uncommitted 변경이나 untracked 파일이 있으면 **실행 거부**, 그 밖의 경로만 dirty하면 **경고 + 헤더 표기 후 진행**한다. 근거: `git worktree add`는 **커밋된 것만 가져간다.** 그 변경이 빠진 트리를 검증해놓고 "우리 프로젝트"라고 부를 수 없다 — 이 스킬이 답하겠다고 한 질문이 그 자리에서 거짓이 된다. 기존 «base 신선도» 절은 이 누수를 **미래 방향으로만** 막았다(검증 후 쌓인 커밋). **과거 방향 — 커밋 안 된 현재 — 은 비어 있었다.** 표면 밖까지 거부하지 않는 이유는 비례성이다: 소스 한 줄 고쳐둔 상태로 리허설을 못 돌리게 하면 스킬이 실용성을 잃고, 표면 밖 변경은 설치·빌드·부팅 결과를 바꾸지 않는다. untracked를 tracked와 같이 다루는 이유는 커밋 안 된 `patches/foo.patch`가 **tracked 여부와 무관하게** 업그레이드 결과를 바꾸기 때문이다.

- **«인자 검증 1을 `node -e`로»** — registry 존재 확인을 `WebFetch`가 아니라 `Bash`의 `node -e` 상태 코드로 한다. 근거: **`WebFetch`는 작은 모델이 요약해 돌려주는 채널**이고, 자매 스킬 `currency`가 실측으로 못 믿는다고 결론 낸 곳이다(ms 타임스탬프를 1년 5개월 틀리게 변환). 그 채널에 **실행 거부 판정**을 걸어두면 존재하는 버전이 요약 오류 하나로 막힌다. **조회가 실패하면 거부하지 않고 `미실행`으로 둔다** — T1 설치 단계가 사실상의 존재 검증이라 없는 버전은 거기서 멈추고, **거짓 404로 존재하는 버전을 거부하는 쪽이 더 나쁜 실패**다(앞은 한 단계 늦게 멈추는 것이고 뒤는 우회 수단이 없다). 검사 2는 인자 문자열만 보므로 검사 1이 미실행이어도 그대로 판정한다.

- **«lockstep 정본 이동»** — 검사 3의 세트 목록을 본문에서 걷어내고 `shared/lockstep-sets.md`를 Read한다. 근거: `currency` 게이트 6과 **같은 목록을 봐야** 한다 — 양쪽에 각각 적으면 한쪽만 늘어나고, 그러면 **`currency`가 권장한 세트를 이 스킬이 "짝 누락"으로 거부한다.** 그 파일의 «잠정 후보»로는 거부하지 않는다(휴리스틱으로 막으면 우회 수단이 없다). 도달 실패 시에도 거부하지 않고 `인자 검증 3 미실행 (lockstep 목록 도달 실패)`로 둔다 — **확인 못 한 것을 위반으로 취급하지 않는다.**

- **«환경 전제 탐지»** — android는 `ANDROID_HOME`/`ANDROID_SDK_ROOT` **+ `adb version`·`emulator -version`**, ios는 macOS 호스트 **+ `xcodebuild -version`·`pod --version`**을 보고, **티어 시작 전에 1회** 판정한다. 근거: `미실행 (Android SDK 없음)` 표기만 있고 **탐지 규칙이 없었다** — 규칙 없이 표기만 두면 에이전트가 빌드 실패를 보고 사후에 "SDK가 없었나 보다"라고 **추측**하고, 추측한 사유를 리포트에 싣는 건 환각 금지 위반이다. **환경변수와 실행 가능 여부를 둘 다 보는 이유**는 변수가 경로 선언일 뿐 실행 가능을 뜻하지 않기 때문이다. **시점이 티어 시작 전인 이유**는 빌드를 절반 돌린 뒤 전제 부재를 발견하면 그게 미실행이 아니라 **실패로 오분류**되고, 그러면 환경 부재와 업그레이드 회귀를 리포트 독자가 못 가리기 때문이다.

- **«단계 타임아웃 4종»** — `step_timeout_install_seconds`(T1 설치) · `step_timeout_check_seconds`(T1 타입체크·테스트) · `step_timeout_build_seconds`(T2 `pod install`·네이티브 빌드) · `step_timeout_boot_seconds`(T2 부팅·로그 스캔)를 `shared/constants.md`에 신설했다. 근거: **어느 단계에도 상한이 없었다.** Gradle 빌드·`pod install`·에뮬레이터 부팅은 네트워크나 데몬에서 멈추면 스스로 끝나지 않는다. **초과는 `실패 (타임아웃 <상수명>)`이지 미실행이 아니다** — 미실행은 "안 돌렸다"는 뜻인데 돌았고 안 끝났다. **멈춘 건 관측된 사실**이고, 미실행으로 적으면 독자가 "그 축을 안 봤다"로 읽는다. **티어가 아니라 단계 단위인 이유**는 Gradle 빌드의 45분과 네트워크에서 멈춘 `pod install`의 45분이 같은 상한을 쓸 수 없기 때문이다. `boot_survival_seconds`(통과 조건)와 `step_timeout_boot_seconds`(상한)는 축이 다르다 — 전자가 후자보다 크면 통과가 구조적으로 불가능해지므로, 그 관계가 깨지면 실행이 아니라 상수가 잘못이다.

- **«베이스라인 필드»** — `베이스라인: 미측정` 또는 `베이스라인: 측정됨 (<사유>)`을 리포트 헤더에 **채택 여부와 무관하게 항상** 싣고, 채택한 실행은 **커밋 메시지에도** 싣는다. 근거: 채택 게이트 3이 *"조건부 베이스라인이 측정되지 않았을 것"*을 요구하는데 그 근거가 **어디에도 안 남았다.** 채택이 끝나면 worktree는 폐기되고 리포트는 같은 타깃 재실행에서 덮어쓰이며 `artifacts/`는 보존 상한에 밀린다 — **커밋만 남는다.** 사후 감사가 가능한 유일한 자리가 거기다. **검증 못 하는 게이트는 게이트가 아니다.** `미검증`도 함께 싣는 이유는 브랜치명이 타깃과 base만 주장하지 **어디까지 봤는지는 말하지 않기** 때문이다.

- **«worktree 경로 상수화»** — `shared/constants.md`에 `worktree_path_template`(`/tmp/rn-rehearsal-<target>-<base_sha7>`)을 신설하고 본문·리포트 어디에도 경로를 직접 적지 않는다. 근거: 경로가 상수도 아니고 스킬 본문에도 없이 **참조 파일 예시에만** 있었다 — 예시가 사실상의 정본이 된 상태다. 같은 경로가 **재현 블록·수동 정리 커맨드·충돌 판정 세 곳에 동시에** 박히므로 한 곳만 고치면 나머지 둘이 조용히 거짓이 된다. **`<base_sha7>`은 장식이 아니다** — 같은 타깃을 **다른 base에서** 동시에 돌릴 때 충돌하지 않게 하려는 것이고, 남는 충돌(같은 타깃·같은 base)은 진짜 충돌이라 거부 대상이다.

- **«기존 디렉토리 처리»** — `git worktree list`에 **없는** 고아 디렉토리는 `git worktree prune` 후 지우고 진행하되 **지웠다는 사실을 리포트 헤더에 적는다.** **등록돼 있으면 `실행 거부 — worktree 사용 중: <경로>`**. 근거: 원안은 폐기 실패만 정의하고 **그 다음 실행이 무엇을 보게 되는지를 비워뒀다.** 등록이 없다는 건 이 경로를 쓰는 실행이 없다는 뜻이라 지워도 안전하다 — **금지된 건 지우는 것이 아니라 조용히 지우는 것이다.** 등록된 경로를 거부하는 이유는 경로에 `<target>`과 `<base_sha7>`이 둘 다 들어가 **같은 타깃·같은 base에서만 충돌**하고, 그건 우연이 아니라 **동시 실행 의심**이기 때문이다. 강제로 걷어내면 돌고 있는 실행의 `node_modules`를 중간에 뽑는다.

- **«T3 스크린샷 수집 방법»** — android `adb exec-out screencap -p`, ios `xcrun simctl io booted screenshot`, **플랫폼당 1장**, 시점은 **`boot_survival_seconds` 생존 확인 직후**. 근거: 커맨드·장수·시점이 정의돼 있지 않으면 재현 블록(*"실제 실행된 것에서 그대로 추출"*)에 실을 줄을 **작문**하게 되고 그건 환각 금지 위반이다. 시점을 생존 확인 뒤로 미루는 이유는 그 전에 찍으면 **스플래시가 찍혀** 증거물이 T2 판정선과 어긋난 화면을 남기기 때문이다. **수집 실패는 T3를 실패로 만들지 않는다** — 스크린샷은 증거물 전용이고 판정 근거가 아니므로 그 부재는 업그레이드에 대한 관측이 아니다. `미실행 (스크린샷 수집 실패: <사유>)`로 남긴다. **늘어난 건 미실행의 사유지 판정이 아니다 — 판정 어휘는 3값 그대로다.**

- **«degrade — 4경로»** — 이 스킬에는 degrade 절이 **아예 없었다.** 4경로: `shared/constants.md` 도달 실패(1) · `shared/lockstep-sets.md` 도달 실패(2) · `node -e` registry 조회 실패(3) · `.rn-upgrade-kit/` 쓰기 실패(4). **1만 실행 거부인 이유**는 이 스킬에서 상수가 **판정 임계값이 아니라 실행 파라미터**이기 때문이다 — `step_timeout_*` 없이는 단계를 돌리다 무한정 멈추고, `boot_survival_seconds` 없이는 T2 통과 조건 자체가 정의되지 않으며, `worktree_path_template` 없이는 격리 공간을 어디에 만들지도 모른다. **실행이 성립하지 않는다.** 자매 스킬의 추정값은 한 줄을 틀리게 하지만 여기서는 수십 분을 돌린 리허설이 **무엇을 검증한 것인지 알 수 없게** 된다. `확인 못 함`은 이 스킬의 어휘가 아니므로 3값 고정을 지키면서 남는 선택지가 거부뿐이고, **거부는 판정이 아니다.** 4의 쓰기 순서는 **채택 커밋 → `artifacts/` → 리포트**다 — 리포트가 마지막인 이유는 앞의 실패를 리포트가 보고할 수 있어야 하기 때문이고, 반대 순서면 **리포트가 인용하는 경로가 거짓이 된다.** 쓰기 실패로 채택을 되돌리지 않는다: 커밋은 검증이 끝난 결과물이고 게이트 3의 사후 감사 근거는 이미 커밋 메시지에 있다.
