# /rehearsal — RN 업그레이드 리허설 룸

격리된 worktree에서 업그레이드를 **실제로 끝까지 수행**하고, 어디까지 갔고 어디서 멈췄는지를 담은 **리포트 하나**를 낸 뒤 worktree를 폐기한다.

리포트가 답하는 질문은 **"이 업그레이드가 안전한가"가 아니다.** "우리 프로젝트에서 이 업그레이드를 시도했을 때 **어디까지 갔고 어디서 멈췄나**"다.

- **사용자 작업 브랜치·소스·`package.json`·네이티브 설정을 어떤 경로로도 수정하지 않는다.** worktree 내부 수정은 격리 공간이므로 이 금지 대상이 아니다.
- **쓰기는 셋**: 리포트 파일 1개 + 상한 있는 `artifacts/` + (채택 시에만) 전용 브랜치 커밋 1개. **`.gitignore`도 수정하지 않는다.**
- **판정 어휘 3값 고정: 통과 · 실패 · 미실행.** "안전/깨짐" 2값 금지. 4번째 어휘를 늘리지 않는다.
- **환각 금지.** 재현 커맨드는 **실제 실행된 것에서 그대로 추출한다** — 작문하면 검증할 수 없는 커맨드를 리포트에 싣게 된다.
- **자동 머지·자동 push·사용자 현재 브랜치 수정은 어떤 조건에서도 하지 않는다.**

## 0. 실행 거부 — 티어 시작 전 관문

**거부는 판정이 아니다.** 어떤 티어도 시작하지 않고 **리포트 파일도 생성하지 않는다.** 반쯤 돌다 이상한 실패를 내는 게 최악이다.

### Windows 호스트

스킬 **최초 단계에서 1회** 호스트를 판별한다. Windows면 즉시 중단하고 사유를 출력한다.

> 근거: RN 네이티브 빌드·CocoaPods·에뮬레이터 제어·worktree 폐기가 전부 Windows에서 별도 경로를 요구하고, 그 경로는 유지보수자가 검증할 수 없다. **검증 못 한 실행 경로를 사실로 쓰지 않는다**는 이 플러그인의 원칙과 정면 충돌한다.

**선언된 미지원이어야 한다** — README에 지원 매트릭스가 있다. 조용한 미지원 금지.

### 인자 검증 3종

목표 버전 세트는 **인자로만** 들어온다. `currency` 리포트를 파싱하지 않는다 — 사람용 리포트를 기계 스키마로 겸용하면 리포트 문구 개선이 이 스킬의 회귀가 된다. **인자가 없으면 실행 거부다. 타깃을 추측하지 않는다.**

| # | 검사 | 실패 시 |
| - | --- | --- |
| 1 | 각 인자가 registry에 **존재하는 버전**인가 — `node -e`로 상태 코드를 직접 읽는다 (아래) | `실행 거부 — 존재하지 않는 버전: <pkg>@<ver>` |
| 2 | **프리릴리즈가 아닌가** — 버전 문자열에 `-`가 있으면 프리릴리즈다 (semver 규칙) | `실행 거부 — 프리릴리즈: <pkg>@<ver>` |
| 3 | **lockstep 짝이 전부 왔나** — 세트 목록은 `../../shared/lockstep-sets.md`를 Read해서 쓴다 | `실행 거부 — lockstep 짝 누락: <빠진 패키지>` |

**짝 하나만 올리는 리허설은 무의미하다** — 반쯤 맞춘 세트로 T2까지 돌면 그 관측이 무엇을 뜻하는지 아무도 모른다.

#### 검사 1 — 존재 확인에 `WebFetch`를 쓰지 않는다

```sh
node -e "fetch('https://registry.npmjs.org/react-native/0.83.4').then(r=>console.log(r.status))"
```

> 위 예시의 패키지·버전은 값이 아니라 예시다 — 실제 값은 인자에서 온다.

- **`WebFetch`는 작은 모델이 요약해 돌려주는 채널이다.** 자매 스킬 `currency`가 실측으로 못 믿는다고 결론 낸 곳이고(ms 타임스탬프를 1년 5개월 틀리게 변환), 요약된 404를 **실행 거부의 판정 근거**로 쓰면 존재하는 버전이 요약 오류 하나로 막힌다. `allowed-tools`에 `Bash`가 있으므로 상태 코드를 직접 읽는다.
- **한 줄·개행 없음·`$`와 백틱 없음.** 같은 인자가 PowerShell을 거쳐도 그대로 전달돼야 한다 — 인용 규칙이 다른 셸에서 조용히 깨지면 아래 degrade로 떨어진 사실조차 안 드러난다.
- **`node -e` 자체가 실패하면 거부하지 마라.** 인자 검증 1을 **미실행**으로 두고 리포트 헤더에 `인자 검증 1 미실행 (registry 조회 실패)`를 적은 뒤 진행한다 — T1 설치 단계가 사실상의 존재 검증이고, 없는 버전이면 거기서 멈춘다. **거짓 404로 존재하는 버전을 거부하는 쪽이 더 나쁜 실패다**: 앞은 리허설이 한 단계 늦게 멈추는 것이고, 뒤는 우회 수단 없이 사용자가 막히는 것이다.
- **검사 2는 조회가 필요 없다.** 인자 문자열만 본다 — 검사 1이 미실행이어도 그대로 판정한다.
- **검사 2는 접미사를 열거하지 않는다.** semver에서 `-` 뒤는 프리릴리즈 식별자이므로 **하이픈 유무 하나로 판정한다.** `-rc`·`-beta`·`-next`·`-canary`만 열거하면 `0.84.0-alpha.3`·`0.0.0-nightly-20260830`이 그 사이로 빠져 **프리릴리즈 리허설이 거부 없이 채택까지 간다.** 자매 스킬 `currency`의 게이트 1은 이미 하이픈 전체를 거른다(`skills/currency/SKILL.md`의 원라이너 `!/-/.test(v)`) — **같은 대상을 두 스킬이 다른 기준으로 판정하면 안 된다.**

#### 검사 3 — lockstep 목록은 공유 파일에서 온다

- **세트를 본문에 박지 않는다.** `currency` 게이트 6과 **같은 목록을 봐야** 한다 — 양쪽에 각각 적으면 한쪽만 늘어나고, 그러면 `currency`가 권장한 세트를 이 스킬이 "짝 누락"으로 거부한다.
- **잠정 lockstep 후보로는 거부하지 않는다.** 거부는 확정 세트로만 한다 — 인자 검증은 사용자가 손으로 친 것을 막는 자리고, 휴리스틱으로 막으면 우회 수단이 없다.
- 파일 도달 실패 시 처리는 그 파일의 «도달 실패» 절을 따른다: 인자 검증 3을 **미실행**으로 두고 헤더에 `인자 검증 3 미실행 (lockstep 목록 도달 실패)`를 적는다. **거부하지 않는다** — 확인 못 한 것을 위반으로 취급하지 않는다.

### 인자 없음 — 거부하되 어디로 갈지 알린다

인자가 없으면 `실행 거부 — 목표 버전 인자 없음`이다. **타깃을 추측하지 않는다.** 다만 거부로 끝내지 않고 고정 문구를 함께 낸다:

> 이 스킬은 목표 버전을 인자로만 받는다. 무엇으로 올려야 할지 아직 모른다면 `currency`가 권장 버전을 산정하고, 그 리포트의 커맨드 블록을 그대로 복붙하면 된다.

**세 스킬 중 여기만 인자 없이 못 도는 자리다.** 사용자 발화 *"RN 업그레이드 …"*는 이 스킬의 트리거 구절과 어휘가 겹치므로 오발동이 실재한다 — 거부만 하고 끝내면 사용자는 아무 답도 못 받는다. **거부는 판정이 아니지만 막다른 길도 아니다.**

### `<target>` 문자 제약 — 경로에 박히기 전에

`<target>`(`references/report-format.md` §`<target>`)은 인자 문자열에서 파생되고, 그 값이 **worktree 경로·리포트 경로·artifacts 경로·브랜치명 네 곳에 박힌다.** 파생 직후 1회 검사한다.

| 검사 | 실패 시 |
| --- | --- |
| `<target>`이 `^[A-Za-z0-9._-]+$`에 맞는가 | `실행 거부 — 타깃 문자 위반: <target>` |

- **이 검사는 «인자 검증 3종»에 번호로 들어가지 않는다.** `../../shared/lockstep-sets.md`가 `인자 검증 3`을 이름으로 참조하므로 번호를 밀지 않는다 — 아래 «작업 트리 검증»과 같은 이유다.
- **인자 검증 1이 이 자리를 대신하지 못한다.** 검사 1은 registry 조회이고 `node -e`가 실패하면 **거부가 아니라 미실행으로 넘어간다**(위) — 즉 registry 404조차 차단선이 아니다. 문자 검사는 조회가 필요 없으므로 **검사 1이 미실행이어도 그대로 판정한다.**
- **왜 경로보다 앞인가**: 허용 문자셋을 좁히지 않으면 `../`나 공백이 섞인 `<target>`이 `/tmp/rn-rehearsal-<target>-<base_sha7>` 접합을 통해 격리 공간 **밖**을 가리키고, §5의 자동 삭제가 그 경로를 지운다. 서두의 *"사용자 작업 브랜치·소스를 어떤 경로로도 수정하지 않는다"*가 **유일하게 삭제 권한을 가진 자리에서** 경로 정의만으로는 지켜지지 않는다.

### git 전제 — 종료 코드로 판정한다

worktree·`base_sha`·채택이 전부 git에 기댄다. **티어 시작 전에 1회 확인한다.**

| 검사 | 실패 시 |
| --- | --- |
| `git rev-parse --is-inside-work-tree` 종료 코드 0 | `실행 거부 — git 저장소가 아니다: <cwd>` |
| `git rev-parse HEAD` 종료 코드 0 | `실행 거부 — 커밋이 없다 (unborn HEAD)` |

- **출력이 아니라 종료 코드를 본다.** git 저장소가 아닌 디렉토리에서 `git status --porcelain`은 **stdout이 비어 있고** 종료 코드가 128이다. 출력만 보는 구현은 그걸 *"변경 없음 = clean"*으로 읽고, 아래 «작업 트리 검증»이 **항상** 싣게 한 헤더 `검증 기준: <base_sha> (작업 트리 clean)`을 `base_sha`도 못 읽은 상태에서 사실로 출력한다 — **환각 금지 위반이 헤더에서 난다.**
- **그 뒤에 오는 오분류가 더 나쁘다.** 확인 없이 진행하면 worktree 생성이 실패하는데 그건 T1의 첫 단계라 `실패`로 기록되고, 수직 fail-fast가 전 티어를 `미실행 (앞 티어 실패)`로 만든다 — 「환경 부재와 업그레이드 회귀를 리포트 독자가 못 가린다」가 그대로 재현된다.
- **거부이지 degrade가 아니다.** §8의 4경로는 전부 "실행은 되는데 재료가 없는" 상태인데, 여기는 실행 자체가 성립하지 않는다.

### 채택 브랜치 선점 — 관문에서는 경고만

`../../shared/constants.md`의 `branch_name_template`으로 조립한 채택 브랜치명이 이미 존재하면, **관문에서 알리되 거부하지 않는다.**

> `채택 예정 브랜치가 이미 존재한다: <이름> — 이 실행은 리포트까지 내고 채택은 막힌다(§6 금지)`

- **거부하지 않는 이유**: 채택은 종단 **옵션**이고 리포트는 그 자체로 산출물이다. 채택이 막힌다고 수십 분짜리 관측을 시작조차 못 하게 하면, 이 스킬이 답하기로 한 질문(*"어디까지 갔고 어디서 멈췄나"*)을 거부가 대신 지워버린다.
- **그런데 침묵도 안 된다**: 알리지 않으면 사용자는 수십 분 뒤 채택 직전에야 막힌 걸 안다. worktree 충돌은 관문에서 잡으면서(§5) 같은 재진입 원인인 브랜치 충돌만 사후 처리인 건 비대칭이다 — **판정 시점은 그대로 두고 고지 시점만 앞으로 당긴다.**

### 작업 트리 검증 — `base_sha` 고정 · dirty tree

**`base_sha`는 실행 시작 시점의 현재 브랜치 HEAD다.** 인자로 받지 않는다 — 이 플러그인의 인자는 **좁히기 전용**이고(§1 `--platform`), base를 인자로 열면 넓히는 인자가 된다. 리허설 시작 전에 `git rev-parse HEAD`로 **한 번 읽어 고정**하고, worktree 경로·브랜치명·리포트 헤더·머지 선행 확인이 전부 그 고정된 값을 쓴다. 도중에 다시 읽으면 네 곳이 서로 다른 커밋을 가리킬 수 있다.

이 검사가 «인자 검증 3종»에 번호로 들어가지 않는 이유는 **인자가 아니라 트리 상태**이기 때문이다. `../../shared/lockstep-sets.md`가 `인자 검증 3`을 이름으로 참조하므로 번호를 밀지 않는다.

`git status --porcelain`으로 판정한다 — 위 «git 전제»가 통과한 뒤이므로 **빈 출력은 clean을 뜻한다.** **untracked 파일도 tracked 변경과 같은 기준으로 다룬다** — 커밋 안 된 `patches/foo.patch`는 tracked 여부와 무관하게 업그레이드 결과를 바꾼다.

| 조건 | 처리 |
| --- | --- |
| **업그레이드 표면**(`package.json` · lockfile · `android/**` · `ios/**` · `patches/**`)에 uncommitted 변경 또는 untracked 파일 | `실행 거부 — 작업 트리 dirty: <경로 목록>` |
| 그 밖의 경로만 dirty | **경고 + 진행.** 리포트 헤더에 dirty 경로 목록을 싣는다 |

- **표면이 dirty면 거부하는 이유**: `git worktree add`는 커밋된 것만 가져간다. 그 변경이 빠진 트리를 검증해놓고 "우리 프로젝트"라고 부를 수 없다 — 서두가 정의한 이 스킬의 질문이 그 자리에서 거짓이 된다. §6의 base 신선도 절은 이 누수를 **미래 방향으로만** 막는다(검증 후 쌓인 커밋). 과거 방향 — 커밋 안 된 현재 — 은 여기서 막는다.
- **그 밖의 경로를 거부하지 않는 이유**: 소스 한 줄 고쳐둔 상태로 리허설을 못 돌리게 하면 스킬이 실용성을 잃는다. 표면 밖 변경은 설치·빌드·부팅 결과를 바꾸지 않으므로 **비례적으로 갈라 경고로 끝낸다.** 대신 무엇이 검증에서 빠졌는지 리포트가 말한다.

리포트 헤더는 **항상** 둘 중 하나를 싣는다:

```
검증 기준: <base_sha> (작업 트리 clean)
검증 기준: <base_sha> (작업 트리 dirty — 검증에 미포함: <경로 목록>)
```

### 산정 시각 주석

`currency` 커맨드 블록에는 `# 산정 시각: YYYY-MM-DD`가 붙는다. 그대로 복붙하면 함께 온다.

- 주석이 오면 **경과일을 리포트 헤더에 남긴다**: `타깃 산정: 2026-08-09 (21일 경과)`.
- 경과일이 `../../shared/constants.md`의 `target_staleness_warn_days`를 넘으면 **실행 전에 경고한다. 거부가 아니라 경고다** — 낡은 타깃도 리허설 자체는 유효하다.
- **주석이 없으면 경고하지 않는다**(손으로 친 경우). 없는 것을 실패로 만들지 않는다.

## 1. 티어 모델

| 티어 | 내용 | 플랫폼 축 |
| --- | --- | --- |
| **T1** | worktree 생성 → PM 감지 → **업그레이드 적용** → 의존성 설치 → 패치 재적용 → 타입체크 → 테스트 | 없음 (공통) |
| **T2/android** | Gradle 빌드 → 에뮬레이터/기기 설치 → 부팅 → 로그 스캔 | android |
| **T2/ios** | `pod install` → `xcodebuild` → 시뮬레이터 부팅 → 로그 스캔 | ios (macOS 호스트만) |
| **T3/\<platform\>** | 스크린샷 수집 — **증거물 전용, 판정 근거 아님** | 부팅 성공한 플랫폼마다 |

### fail-fast는 수직에만

- **수직(티어 간)**: T1 실패 → 모든 T2·T3 미실행. T2/android 실패 → T3/android 미실행.
- **수평(플랫폼 간)에는 적용하지 않는다.** `T2/android` 실패가 `T2/ios`를 막지 않는다.
- 실행 **순서**는 싼 것부터(android → ios). **순서는 출력 편의일 뿐 게이트가 아니다. 순서 ≠ 의존.**

### 미실행 사유 5종 — 반드시 구분 표기

| 사유 | 표기 |
| --- | --- |
| fail-fast | `미실행 (앞 티어 실패)` |
| 호스트·환경 전제 미충족 | `미실행 (macOS 필요)` / `미실행 (Android SDK 없음)` / `미실행 (Xcode 없음)` / `미실행 (CocoaPods 없음)` / `미실행 (Android 기기 없음)` / `미실행 (iOS 시뮬레이터 없음)` / `미실행 (<축> 기기 다중 — 하나만 남기고 재실행)` |
| 사용자 지정 스코프 | `미실행 (사용자 지정 스코프)` |
| 개입 필요로 중단 | `미실행 (패치 불완전으로 중단)` |
| 증거물 수집 실패 | `미실행 (스크린샷 수집 실패: <사유>)` |

**"요청 안 함"과 "못 함"은 다른 사유다.** 합치지 마라 — 합치면 리포트 독자가 "iOS를 안 본 게 내 선택이었나 환경 탓이었나"를 못 가린다.

**5번째는 T3에만 붙는다** — T3는 판정 티어가 아니므로 증거물을 못 모은 것이 실패 판정이 되지 않는다(§4). **늘어난 건 미실행의 사유지 판정이 아니다. 판정 어휘는 3값 그대로다.**

### 환경 전제 탐지 — 티어 시작 전 1회

`미실행 (Android SDK 없음)` 같은 표기는 **탐지 규칙이 있어야 쓸 수 있다.** 규칙 없이 표기만 두면 에이전트가 빌드 실패를 보고 사후에 "SDK가 없었나 보다"라고 추측한다 — 추측한 사유를 리포트에 싣는 건 환각 금지 위반이다.

| 축 | 확인 | 하나라도 실패하면 |
| --- | --- | --- |
| android | `ANDROID_HOME` 또는 `ANDROID_SDK_ROOT` 설정 + `adb version` + `emulator -version` | T2/android·T3/android = `미실행 (Android SDK 없음)` |
| android | `adb devices`에 `device` 상태 항목이 **정확히 1개** | 0개 → `미실행 (Android 기기 없음)` / 2개 이상 → `미실행 (Android 기기 다중 — 하나만 남기고 재실행)` |
| ios | 호스트가 macOS + `xcodebuild -version` | T2/ios·T3/ios = `미실행 (macOS 필요)` / `미실행 (Xcode 없음)` |
| ios | `pod --version` | T2/ios·T3/ios = `미실행 (CocoaPods 없음)` |
| ios | `xcrun simctl list devices booted`에 항목이 **정확히 1개** | 0개 → `미실행 (iOS 시뮬레이터 없음)` / 2개 이상 → `미실행 (iOS 시뮬레이터 다중 — 하나만 남기고 재실행)` |

- **환경변수와 실행 가능 여부를 둘 다 본다.** 변수는 경로 선언일 뿐 실행 가능을 뜻하지 않는다 — 변수만 보고 통과시키면 `adb`가 없는 호스트에서 T2/android가 시작되고, 그 실패가 업그레이드 회귀처럼 보인다.
- **바이너리 유무와 기기 기동 여부도 둘 다 본다.** SDK는 깔려 있고 기기는 안 떠 있는 호스트가 가장 흔하다 — 바이너리만 보고 통과시키면 T2가 시작돼 `실패`로 기록되고, 그게 바로 이 절이 막으려는 오분류다. **§3의 통과 조건 3개는 전부 앱이 떠 있어야 관측된다** — 띄울 기기가 없으면 관측이 아니라 부재다.
- **하나도 없을 때와 여럿일 때를 가른다.** `adb install`과 `xcrun simctl … booted`는 **대상이 하나라고 전제하는 커맨드다** — 기기가 둘이면 `adb`는 `more than one device`로 죽고 `booted`는 어느 시뮬레이터인지 모호해진다. 조용히 하나를 고르면 리포트가 **어느 기기에서 관측했는지 말할 수 없는 판정**을 싣게 된다. 둘 다 `미실행`이지만 사용자가 할 일이 반대라(하나 띄우기 / 하나 남기기) **표기를 합치지 않는다.**
- **`-s <serial>`로 기기를 지정하는 경로를 만들지 않는다.** 인자를 하나 늘리면 «인자는 좁히기 전용»이 깨지고, 어느 기기가 맞는지는 이 스킬이 알 수 없다. 사용자가 정리하는 쪽이 정확하다.
- **기기·시뮬레이터를 이 스킬이 띄우지 않는다.** AVD 생성·이미지 선택·시뮬레이터 런타임 설치는 호스트 프로비저닝이고, 리허설 룸의 범위가 아니다 — `미실행` 사유를 정확히 적고 사용자가 띄우게 한다. **없는 것을 만들어내는 대신 없다고 말한다.**
- **탐지는 티어 시작 전에 한다.** 빌드를 절반 돌린 뒤 전제 부재를 발견하면 그건 미실행이 아니라 **실패로 오분류된다** — 환경 부재와 업그레이드 회귀를 리포트 독자가 못 가린다.
- **전제 미충족은 실행 거부가 아니다.** 다른 축은 그대로 돌린다 — 수평(플랫폼 간)에는 fail-fast를 적용하지 않는다는 위 규칙의 연장이다.

### 단계 타임아웃

**어느 단계도 무한정 기다리지 않는다.** Gradle 빌드·`pod install`·에뮬레이터 부팅은 네트워크나 데몬에서 멈추면 스스로 끝나지 않고, 상한이 없으면 스킬 전체가 거기 갇힌다.

| 단계 | 상한 (`../../shared/constants.md`) |
| --- | --- |
| T1 의존성 설치 | `step_timeout_install_seconds` |
| T1 타입체크 · 테스트 (각각) | `step_timeout_check_seconds` |
| T2 `pod install` · 네이티브 빌드 (각각) | `step_timeout_build_seconds` |
| T2 부팅 + 로그 스캔 | `step_timeout_boot_seconds` |

- 초과 시 판정은 **`실패 (타임아웃 <상수명>)`**이지 미실행이 아니다. **멈춘 건 관측된 사실이다** — 미실행은 "안 돌렸다"는 뜻인데 돌았고 안 끝났다. 미실행으로 적으면 리포트 독자가 이 실행을 "그 축을 안 봤다"로 읽는다.
- 타임아웃 실패에도 **수직 fail-fast가 그대로 적용된다.** 뒤 티어는 `미실행 (앞 티어 실패)`다.
- **`boot_survival_seconds`는 통과 조건이고 `step_timeout_boot_seconds`는 상한이다** — 앱이 살아 있어야 하는 **최소** 시간과 부팅 단계를 기다려주는 **최대** 시간이라 축이 다르다. 전자가 후자보다 크면 통과가 구조적으로 불가능해지므로, 그 관계가 깨지면 실행이 아니라 상수가 잘못이다.
- **재현 블록에 `timeout` 래퍼를 넣지 마라.** 상한은 스킬이 단계를 감싸 건 것이지 사용자가 친 커맨드의 일부가 아니다 — 넣으면 *"실제 실행된 것에서 그대로 추출"*이 깨진다. 대신 **타임아웃으로 끝난 단계에만** 그 줄 위에 주석 한 줄을 단다: `# 이 단계는 <상수명> 초과로 중단됐다`.

### 오염 플래그 — 판정 축과 직교

`[패치 불완전]`은 **판정 어휘가 아니다.** 3값은 그대로 유지된다.

- 플래그가 붙은 실행의 **어떤 관측도 "통과"로 단독 인용될 수 없다.**
- 패치 실패 시 T1 판정 = **실패**. 단 수집된 관측(tsc·test 결과)은 버리지 않고 전부 플래그를 달아 싣는다 — 정보를 통째로 잃지 않기 위함이다.

### `--platform` — 좁히기 전용

기본값은 항상 **호스트가 허용하는 플랫폼 전부**다. **넓히는 방향의 인자는 두지 않는다** — 기본값이 항상 가장 많이 검증하는 쪽에 선다. 제외된 플랫폼은 조용히 빠지지 않고 `미실행 (사용자 지정 스코프)`로 명시된다.

## 2. T1 — 설치 · 패치 · 검사

### PM 감지 (기계적)

lockfile 기반 1회 감지. `Glob`으로 탐지한다.

| lockfile | PM | 적용 | 설치 | 패치 메커니즘 (우선순위) |
| --- | --- | --- | --- | --- |
| `pnpm-lock.yaml` | pnpm | `pnpm add <pkg>@<ver>…` | `pnpm install --frozen-lockfile` | `patches/` + `patchedDependencies` → `patch-package` |
| `package-lock.json` | npm | `npm install <pkg>@<ver>…` | `npm ci` | `patch-package` (postinstall) |
| `yarn.lock` | yarn | `yarn add <pkg>@<ver>…` | `yarn install --immutable` | `.yarn/patches` + resolutions → `patch-package` |
| `bun.lock` / `bun.lockb` | bun | `bun add <pkg>@<ver>…` | `bun install --frozen-lockfile` | `patches/` + `patchedDependencies` → `patch-package` |

- **PM 네이티브 메커니즘 우선.** `patch-package`는 폴백.
- lockfile이 둘 이상이면 실행 거부가 아니라 **T1 실패**로 처리하고 사유를 명시한다(`PM 판별 불가: lockfile 2종 존재`).

### worktree 고정 — 모든 단계는 격리 공간 안에서

**worktree 생성 이후 T1·T2·T3의 모든 커맨드는 worktree 안에서 돈다.** 예외는 없다.

- 첫 단계에서 worktree로 이동하고, git 호출은 **`git -C <worktree>`**로 대상을 명시한다. 상대 경로에 기대지 마라 — `cd` 한 번이 빠지면 설치·적용 커맨드가 **사용자 트리에서** 돌고, 서두의 *"`package.json`을 어떤 경로로도 수정하지 않는다"*가 그 한 줄로 깨진다.
- **사용자 저장소에서 도는 커맨드는 §0의 관문 검사뿐이다** — `git rev-parse`·`git status --porcelain`·브랜치 선점 확인. 전부 읽기이고 worktree 생성 **이전**이다.
- 이 규칙은 산문이 아니라 **재현 블록의 형태로도 강제된다**: `references/report-format.md` §재현 커맨드 시퀀스가 첫 두 줄을 `git worktree add` → `cd <worktree>`로 못박고, 그 뒤 모든 줄이 그 안에서 돈다.

### 업그레이드 적용 — T1이 실제로 바꾸는 유일한 지점

**이 단계가 없으면 리허설은 원본 버전을 검증하고 통과를 보고한다.** 전 티어 통과 → 채택 게이트 4개 충족 → **아무것도 업그레이드하지 않은 브랜치**가 `rn-upgrade/<target>-<base_sha7>`이라는 이름으로 남는다. 리포트·브랜치명·커밋 메시지가 전부 거짓을 주장하는 상태이고, 이건 이 스킬이 가장 싫어하는 실패(*"stale 산물이 만드는 거짓 통과"*)와 같은 모양이다. **단계 목록에서 빠지면 조용히 이렇게 된다 — 그래서 티어 표에 이름으로 박혀 있다.**

- **커맨드는 위 PM 표의 «적용» 열이다.** 인자로 받은 세트 **전체를 한 번에** 넘긴다 — 짝을 나눠 부르면 중간 상태에서 peer 해석이 달라진다.
- **`<pkg>@<ver>`는 인자에서 그대로 온다.** 버전을 재해석하거나 반올림하지 않는다 — 인자 검증 2가 프리릴리즈를 이미 걸렀고, 그 밖의 판단은 `currency` 소관이다.
- **선언 범위 표기(`^0.83.4` 대 `0.83.4`)는 PM 기본값을 그대로 둔다.** 이 스킬은 프로젝트의 의존성 표기 정책을 바꾸지 않는다 — 대신 적용 직후 **설치된 실제 버전이 인자와 같은지** 확인하고, 다르면 `T1 실패 (적용 버전 불일치: <pkg> 요청 <ver> / 설치 <실제>)`로 남긴다. 표기를 강제하는 대신 결과를 관측한다.
- **적용이 실패하면 T1 실패다** (`T1 실패 (업그레이드 적용 실패: <사유>)`). 미실행이 아니다 — 돌았고 안 됐다. peer 충돌로 PM이 거부하는 것도 여기 포함되며, **그게 바로 이 리허설이 알아내려던 사실이다.**

#### 적용 다음에 잠금 설치가 오는 이유

«적용» 열이 lockfile을 갱신하고, «설치» 열은 그 lockfile을 **잠근 채로 검증한다.** 순서가 반대이거나 적용이 빠지면 잠금 설치가 `package.json`↔lockfile 불일치로 즉시 에러를 내고, 그 에러가 **업그레이드 회귀로 리포트에 실린다** — 실제로 멈춘 건 단계 순서인데.

- `pnpm add`·`npm install <pkg>@<ver>`·`yarn add`·`bun add`는 **전부 lockfile을 함께 갱신한다.** 그래서 뒤따르는 `--frozen-lockfile`·`npm ci`·`--immutable`은 모순이 아니라 **적용 결과가 완결적인지 확인하는 검사**다.
- 이 두 줄을 **재현 블록에도 나란히 싣는다.** 한 줄만 실으면 복붙한 사용자가 위와 같은 거짓 실패를 재현한다.

### 검사 스크립트가 없는 프로젝트

타입체크·테스트는 **있을 때만 돈다.** 없는 검사를 실패로 만들지 않는다.

| 조건 | 처리 |
| --- | --- |
| `tsconfig.json` 없음 | 타입체크 단계 = `미실행 (프로젝트에 tsconfig.json 없음)` |
| `package.json`의 `scripts.test` 없음 | 테스트 단계 = `미실행 (프로젝트에 test 스크립트 없음)` |

- **이건 단계 표기이지 티어 판정이 아니다.** 판정 어휘 3값도, §1의 미실행 사유 5종(티어 축)도 그대로다 — 늘어난 건 **T1 안쪽 단계의 표기**다.
- **남은 단계로 T1을 판정한다.** 둘 다 없으면 T1은 설치·패치까지로 판정된다. 없는 검사를 `실패`로 적으면 테스트 없는 repo는 영원히 T2를 못 보고, `통과`로 적으면 리포트가 돌지 않은 검사를 통과로 주장한다 — **둘 다 거짓이라 세 번째 표기가 필요하다.**
- **§6의 채택 확인 문구에 그대로 싣는다.** 검사가 적을수록 채택의 근거가 얇다는 사실이 사용자에게 보여야 한다. 게이트 3(베이스라인 미측정)은 이 경우 자동으로 충족되는데, **그건 검사가 깨끗해서가 아니라 검사가 없어서다** — 구분하지 않으면 게이트 3이 보증하는 내용이 조용히 비어버린다.

### 패치 재적용 실패

1. hunk 실패 → 실행에 `[패치 불완전]` 부착
2. **붙은 패치만 적용된 상태로 T1 나머지(타입체크·테스트)를 계속 진행** — 정보 수집
3. T1 판정 = **실패**, T2 이후 `미실행 (패치 불완전으로 중단)`
4. 실패한 패치의 대상 패키지·hunk 번호를 리포트에 명시

### 베이스라인 — 조건부 대조군

**통과 시 비용 0. 실패했을 때만 지불한다.**

1. 업그레이드 적용 후 T1을 먼저 돌린다.
2. 타입체크 또는 테스트가 실패하면 **그때만** 같은 worktree를 업그레이드 전 상태로 되돌려 재측정한다.
3. 판정은 **델타**로 서술한다: `신규 에러 N개 / 기존 부채 M개`.
4. **신규 에러 0이면 T1은 통과다** — 기존 부채는 업그레이드 산물이 아니다.

> 이 절이 없으면 이미 깨져 있는 레포에서 T1은 영원히 실패로 나오고 스킬 전체가 쓸모없어진다.

### 캐시

worktree는 매번 신규 생성되므로 `node_modules`·`Pods`는 매번 새로 깔린다. **worktree 내부에 캐시를 남기지 않는다.**

- 유일한 캐시 의존은 **호스트 전역 store**: pnpm store / yarn cache / npm cache / `~/.gradle` / CocoaPods 캐시.
- **worktree 재사용·`node_modules` 복사·하드링크 주입은 하지 않는다** — stale 산물이 만드는 거짓 통과가 이 스킬이 가장 싫어하는 실패 모드다.

## 3. T2 — 부팅 판정선

**판정선: 첫 프레임 렌더 + 생존 + 로그 클린 — 아래 통과 조건 3개가 관측하는 것까지다.** "로그인 화면 도달"은 판정선이 아니다 — 어느 조건도 그려진 화면의 정체를 관측하지 않으므로, 그 문구를 통과 정의에 실으면 통과 문구 자체가 환각이 된다. 인증 이후 화면은 **비범위**다.

통과 조건 (전부 충족):

1. 앱 프로세스가 `boot_survival_seconds`(`../../shared/constants.md`) 동안 생존
2. **첫 프레임 렌더 신호 관측** — RN 브리지/Fabric 마운트 완료
3. **로그 스캔 클린** — 패턴 목록은 `references/log-patterns.md`

### 기동 — 빌드 산물을 어떻게 올리고 띄우나

**위 통과 조건 3개는 전부 앱이 떠 있어야 관측된다.** 그런데 「빌드」와 「로그 스캔」 사이에는 *설치*와 *실행*이 있고, 그 커맨드가 정의돼 있지 않으면 에이전트가 작문한다 — §4가 스크린샷 커맨드를 못박은 이유(*"정의돼 있지 않으면 재현 블록에 실을 줄을 작문하게 된다 — 환각 금지 위반"*)가 **여기에 더 크게 적용된다.** 스크린샷은 증거물이지만 기동은 판정 경로다.

**커맨드는 worktree 안에서 돈다**(§2 «worktree 고정»). 기기는 이미 떠 있다 — 없으면 §1의 환경 전제에서 `미실행`으로 갈렸다.

#### android

| 단계 | 커맨드 |
| --- | --- |
| 빌드 | `cd android && ./gradlew assembleDebug` |
| 설치 | `adb install -r android/app/build/outputs/apk/debug/app-debug.apk` |
| 실행 | `adb shell monkey -p <applicationId> -c android.intent.category.LAUNCHER 1` |

- **`<applicationId>` 도출**: `android/app/build.gradle`(또는 `build.gradle.kts`)의 `defaultConfig`에 있는 `applicationId` 값을 Read로 읽는다. 이 값이 **`references/log-patterns.md`의 `<applicationId>`와 같은 값**이다 — 두 자리가 다른 출처를 쓰면 로그 스캔이 다른 앱을 본다.
- **`monkey`로 띄우는 이유**: 액티비티명(`.MainActivity`)을 따로 도출하지 않아도 된다. 런처 인텐트로 여는 것은 사용자가 아이콘을 누르는 것과 같은 경로이고, **도출 규칙을 하나 줄이면 작문할 자리도 하나 줄어든다.**
- `applicationId`를 못 읽으면 **T2/android 실패** (`T2/android 실패 (applicationId 도출 불가)`). 환경 부재가 아니라 프로젝트 형태 문제다.

#### ios

| 단계 | 커맨드 |
| --- | --- |
| pods | `cd ios && pod install` |
| 빌드 | `xcodebuild -workspace ios/<Name>.xcworkspace -scheme <Name> -configuration Debug -sdk iphonesimulator -derivedDataPath build` |
| 설치 | `xcrun simctl install booted build/Build/Products/Debug-iphonesimulator/<Name>.app` |
| 실행 | `xcrun simctl launch booted <bundleId>` |

- **`<Name>` 도출**: `pod install` **이후** `Glob`으로 `ios/*.xcworkspace`를 찾아 그 basename을 쓴다. 스킴명도 같은 값이다 — RN 템플릿이 워크스페이스·스킴·`.app`에 같은 이름을 쓴다. 이 값이 `references/log-patterns.md`의 **`<앱이름>`**이다.
- **`<bundleId>` 도출**: `/usr/libexec/PlistBuddy -c "Print :CFBundleIdentifier" build/Build/Products/Debug-iphonesimulator/<Name>.app/Info.plist`. **빌드 산물에서 읽는다** — `project.pbxproj`에서 파싱하면 빌드 설정 변수(`$(PRODUCT_BUNDLE_IDENTIFIER)`)가 안 풀린 문자열을 얻는다.
- `<bundleId>`를 읽지 못하면 **T2/ios 실패** (`T2/ios 실패 (bundleId 도출 불가)`). android의 `applicationId 도출 불가`와 같은 자리다 — **빌드는 됐는데 띄울 대상을 모르는 상태**이고, 환경 부재가 아니다.
- `ios/*.xcworkspace`가 **0개이거나 2개 이상**이면 **T2/ios 실패** (`T2/ios 실패 (스킴 판별 불가: <발견 목록>)`). 조용히 하나를 고르지 않는다 — 「PM 판별 불가: lockfile 2종 존재」가 실행 거부가 아니라 T1 실패인 것과 같은 자리다. **프로젝트 형태가 모호한 것은 환경 부재가 아니다.**

#### 판정 경계

- **설치·실행 단계의 실패는 T2 실패다.** 기기가 있는데 못 올렸거나 못 띄운 것은 관측된 사실이다 — `미실행`은 §1의 환경 전제가 걸렀을 때만 쓴다.
- **도출된 값을 셸에 보간할 때는 큰따옴표로 감싼다** — `<applicationId>`·`<Name>`·`<bundleId>`는 프로젝트 파일과 빌드 산물에서 읽은 값이라 이 스킬이 문자셋을 검사하지 않았다(§0의 문자 제약은 `<target>`에만 걸린다). §5의 삭제 커맨드 인용 규칙과 같은 이유다: **검사하지 않은 값은 인용으로 막는다.**
- **여기서 나온 커맨드는 전부 실제 실행된 형태로 재현 블록에 실린다.** 서두의 *"재현 커맨드는 실제 실행된 것에서 그대로 추출한다"*가 적용되는 대상이고, 도출된 `<applicationId>`·`<Name>`·`<bundleId>`는 **치환된 실제 값으로** 실린다.

### 인증은 스킬 책임이 아니다

테스트 계정 크리덴셜·토큰·스토리지 스냅샷 주입·자동 로그인 스크립트 — **전부 만들지 않는다.** 인증을 스킬 안으로 끌어들이는 순간 스킬이 앱별 비밀에 물린다. **리허설 룸은 앱 비밀을 몰라야 한다.**

리포트는 이 한계를 명시한다: `T2 통과 = 첫 프레임 렌더 + 생존 + 로그 클린. 어느 화면까지 갔는지는 관측하지 않는다 — 인증 이후는 미검증(비범위).`

## 4. T3 — 증거물

- 스크린샷은 **증거물 전용. 판정에 절대 쓰지 않는다.**
- **픽셀 diff 판정 금지.** 지도 타일·애니메이션 프레임·폰트 렌더링 차이가 거짓 양성을 양산한다.
- 부팅에 성공한 플랫폼마다 수집한다.

### 수집 방법 — 커맨드 · 장수 · 시점

수집 커맨드가 정의돼 있지 않으면 재현 블록에 실을 줄을 작문하게 된다 — 환각 금지 위반이다. **커맨드·장수·시점을 못박는다.**

| 축 | 커맨드 |
| --- | --- |
| android | `adb exec-out screencap -p > <artifacts>/android-boot.png` |
| ios | `xcrun simctl io booted screenshot <artifacts>/ios-boot.png` |

- **플랫폼당 1장.** 여러 장은 판정에 안 쓰이는 증거물의 용량만 늘린다 — `artifact_retention_n`이 `report_retention_n`보다 훨씬 작은 이유가 이 스킬이 쌓는 매체의 크기다(`../../shared/constants.md`).
- **시점은 `boot_survival_seconds` 생존 확인 직후.** 그 전에 찍으면 스플래시가 찍히고, 증거물이 §3의 판정선(첫 프레임 이후 생존한 화면)과 어긋난 화면을 남긴다.
- **수집 실패는 T3를 실패로 만들지 않는다.** `미실행 (스크린샷 수집 실패: <사유>)`로 남긴다 — 스크린샷은 판정에 절대 쓰지 않으므로(위) 그 부재는 업그레이드에 대한 관측이 아니다. 이미 난 T2 판정도 바뀌지 않는다.

## 5. worktree 수명 · 산출물

**매번 신규 생성 → 항상 즉시 폐기.** 실패해도 보존하지 않는다. 채택해도 폐기하고 **커밋만 남는다.**

- 생성 경로는 `../../shared/constants.md`의 `worktree_path_template`이다. **본문에도 리포트에도 경로를 직접 적지 마라** — 그 경로는 재현 블록·수동 정리 커맨드·충돌 판정 **세 곳에 동시에** 박히고, 한 곳만 고치면 나머지 둘이 조용히 거짓이 된다.
- 폐기 전에 진단 증거(빌드 로그·logcat·tsc 출력·테스트 출력·스크린샷)를 worktree 밖 `artifacts/`로 복사한다.
- **폐기 실패를 조용히 넘기지 마라.** 리포트에 명시 + 수동 정리 커맨드 제공(`git worktree remove --force <path>`, `git worktree prune`). 조용히 넘기면 "항상 폐기"라는 계약이 거짓말이 되고 누적 문제가 그대로 돌아온다.
- **`artifacts/` 보존 상한 초과분은 자동으로 지운다.** 자매 두 스킬(`platform-watch`·`currency`)은 같은 자리에서 수동 정리 커맨드만 내는데, 그 둘에는 파일 삭제 수단이 없고 이 스킬은 `Bash`에 용도 제한이 없기 때문이다. **세 스킬이 달라지는 게 맞다 — 도구가 다르다.**

### 삭제 커맨드 — 세 자리 모두 이 형태로만

이 스킬은 세 자리에서 삭제한다: **worktree 폐기 · `artifacts/` 덮어쓰기 전 정리 · 보존 상한 초과분.** 셋 다 아래 형태를 쓴다. **커맨드를 작문하지 마라** — 삭제는 이 플러그인에서 유일하게 되돌릴 수 없는 동작이고, 대상 경로가 `<target>`(사용자 인자 파생)을 포함한다.

| 대상 | 커맨드 |
| --- | --- |
| worktree (정상) | `git worktree remove --force "<worktree_path>"` |
| worktree (등록 잔재) | `git worktree prune` |
| `artifacts/` 디렉토리 | `rm -rf "<artifacts_root>/<디렉토리명>"` — `<artifacts_root>`는 `references/report-format.md` §경로가 정의한 `artifacts/` 경로다 |
| 고아 디렉토리 | 아래 «고아 디렉토리 삭제 전 확인» 2가지를 통과한 뒤 `rm -rf "<worktree_path>"` |

- **경로는 항상 큰따옴표로 감싼다.** `<target>`은 §0의 문자 제약을 통과했으므로 공백·`../`가 없지만, **인용은 그 검사가 미래에 느슨해져도 남는 두 번째 방어선이다.**
- **`rm -rf`의 대상은 항상 완성된 단일 경로다.** 와일드카드·변수 접합을 셸에 맡기지 마라 — 지울 디렉토리 목록은 먼저 `Glob`으로 확정하고 **한 번에 하나씩** 지운다.
- **삭제한 것은 전부 리포트에 적는다.** 개수(보존 상한 정리)든 경로(고아 디렉토리)든, **조용히 지우는 것이 금지 대상이다.**

#### 고아 디렉토리 삭제 전 확인

`worktree_path_template`이 만드는 경로는 `<target>`과 `<base_sha7>`만으로 **완전히 예측 가능**하고, `/tmp`는 공용 쓰기 가능 디렉토리다. **git 등록이 없다는 사실은 그 경로가 우리 것이라는 증거가 아니다** — 같은 이름을 다른 프로세스가 먼저 만들어 뒀을 수 있다. 지우기 전에 둘 다 확인한다:

| # | 확인 | 실패 시 |
| - | --- | --- |
| 1 | 그 경로가 **심볼릭 링크가 아닐 것** — `test ! -L "<경로>"` | `실행 거부 — 고아 경로가 심볼릭 링크다: <경로>` |
| 2 | 경로가 `worktree_path_template`의 **리터럴 접두사**(`<target>` 앞부분)로 시작할 것 | `실행 거부 — 고아 경로가 템플릿 밖이다: <경로>` |

- **1이 없으면 삭제가 링크를 따라간다.** `rm -rf`는 링크 자체를 지우지만 `rm -rf <링크>/`나 그 안쪽을 도는 정리는 대상까지 따라가고, 예측 가능한 `/tmp` 경로는 그걸 심어두기 가장 쉬운 자리다.
- **2는 접두사를 상수에서 파생한다.** `worktree_path_template`에서 첫 플레이스홀더(`<target>`) 앞까지를 잘라 쓴다 — **여기에 경로를 리터럴로 적지 않는 것은 §5 서두의 «본문에도 리포트에도 경로를 직접 적지 마라»를 이 절도 지키기 때문이다.** 상수가 바뀌면 접두사가 따라 바뀌어야 하는데, 적어두면 안 따라온다.
- **거부이지 우회가 아니다.** 두 확인 중 하나라도 실패하면 지우지 않고 **실행을 거부한다** — 이상한 상태의 `/tmp` 경로를 스킬이 알아서 정리하는 것보다 사람이 보는 쪽이 낫다.

### 기존 디렉토리를 만났을 때

위 폐기 실패의 다음 실행이 마주치는 상태다. **조용히 지우지 마라 — 다른 실행이 쓰는 중일 수 있다.**

| 조건 | 처리 |
| --- | --- |
| `git worktree list`에 **없는** 고아 디렉토리 | `git worktree prune`으로 등록 잔재를 정리한 뒤 디렉토리를 지우고 진행한다. **지웠다는 사실을 리포트 헤더에 적는다** |
| `git worktree list`에 **등록돼 있음** | `실행 거부 — worktree 사용 중: <경로>` + 아래 탈출 커맨드 |

- **등록이 없다는 건 이 경로를 쓰는 실행이 없다는 뜻이다** — 지워도 안전하다. 금지된 건 지우는 것이 아니라 **조용히** 지우는 것이다.
- **등록된 경로를 거부하는 이유**: `worktree_path_template`은 `<target>`과 `<base_sha7>`을 둘 다 포함하므로 **같은 타깃·같은 base**에서만 충돌한다. 그건 우연이 아니라 **동시 실행 의심**이다. 강제로 걷어내면 돌고 있는 실행의 `node_modules`를 중간에 뽑는다.
- **거부에 탈출 커맨드를 함께 낸다.** 등록된 worktree는 동시 실행뿐 아니라 **중단된 실행의 잔재**로도 생긴다(리포트를 쓰기 전에 턴이 끝나면 폐기가 안 돈다). 그 경우 같은 타깃·같은 base 재실행이 **영구히** 거부되는데, 복구 커맨드는 「폐기 실패」 리포트 절에만 있고 **중단된 실행은 그 리포트를 쓰지 못했다.** 거부 문구에 붙인다:

  ```sh
  # 돌고 있는 실행이 없다는 걸 확인한 뒤에만 실행하라
  git worktree remove --force "<경로>"
  git worktree prune
  ```

  **판정은 그대로 거부다** — 스킬이 알아서 걷어내지 않는다. 바뀐 건 사용자가 빠져나올 길이 리포트가 아니라 **거부 문구 안에** 있다는 것뿐이다.

경로·`<target>` 정의·보존 규칙은 **`references/report-format.md`**에 있다. 조회가 끝난 뒤에 Read한다.

## 6. 채택 (adopt)

리허설이 검증한 결과물을 버리지 않고 전용 브랜치로 남기는 **종단 옵션**. 새 변경 엔진이 아니라 **"안 버리는 것"**이다 — 모든 티어를 통과한 시점에 worktree 안에는 이미 검증된 결과물이 있고, 채택은 그것을 커밋할 뿐이다.

```
worktree 안에서 브랜치 생성 → 커밋  →  worktree 폐기  →  브랜치만 살아남음
```

### 브랜치 생성 — detached에서 브랜치로

worktree는 `git worktree add <path> <base_sha>`로 **`base_sha`에 detach된 상태**로 만들어진다(§5). 브랜치를 만들지 않고 커밋한 뒤 worktree를 폐기하면 **그 커밋은 아무 참조도 없이 남아** 위 그림의 *"브랜치만 살아남음"*이 성립하지 않는다. 채택이 확정된 시점에 이 순서로 만든다:

```sh
git -C "<worktree_path>" checkout -b "<branch_name>"
git -C "<worktree_path>" commit -am "<커밋 메시지>"
```

- **브랜치명은 `../../shared/constants.md`의 `branch_name_template`에서 조립한다.** 본문에 형태를 직접 적지 마라 — 그 이름은 **브랜치 생성·선점 확인(§0)·채택 절·머지 커맨드·커밋 메시지 다섯 곳**에 박힌다. `worktree_path_template`을 상수로 올린 사유(*"세 곳에 동시에 박힌다"*)가 여기서는 다섯 곳이다.
- **브랜치는 채택이 확정된 뒤에만 만든다.** 게이트 4개를 통과하고 사용자가 명시 확인한 다음이다 — 미리 만들면 채택하지 않은 실행이 브랜치를 남기고, 다음 실행이 §0의 «채택 브랜치 선점» 경고를 맞는다.
- **`checkout -b`는 worktree 안에서 돈다.** 사용자 저장소의 HEAD는 움직이지 않는다 — worktree는 자기 HEAD를 따로 갖는다. 이게 «사용자 현재 브랜치에 직접 커밋·체크아웃» 금지와 채택이 양립하는 이유다.

### 게이트 4개 (전부 만족해야 함)

1. 실행된 모든 티어가 `통과` — `실패`가 하나도 없을 것
2. `[패치 불완전]` 오염 플래그 없음
3. **조건부 베이스라인이 측정되지 않았을 것** — 업그레이드 후 검사가 처음부터 깨끗했을 것. 베이스라인이 돌았다는 건 검사가 한 번 실패했고 그게 `기존 부채`로 설명됐다는 뜻이다. 그 실행의 T1은 통과지만 **"기존 부채와 업그레이드 산물이 같은 파일에서 겹치지 않는다"는 보증이 없다** — 게이트 1로는 안 걸린다
4. 사용자 명시 확인 (기본값은 항상 미채택)

**하나라도 어긋나면 채택 옵션을 제시조차 하지 않는다.** "통과했지만 조건부"인 상태에서 적용을 권하면 이 스킬이 지켜온 *"통과 ≠ 안전"*이 무너진다.

`미실행`은 게이트를 막지 않되(호스트 제약·사용자 스코프는 실패가 아니다) **확인 문구에 무엇이 검증되지 않았는지 명시한다.**

**티어의 `미실행`뿐 아니라 T1 안쪽 단계의 미실행도 함께 싣는다** — §2 «검사 스크립트가 없는 프로젝트»의 두 표기가 그 대상이다. 검사가 없는 프로젝트에서는 게이트 3(베이스라인 미측정)이 **자동으로** 충족되는데, 그건 검사가 깨끗해서가 아니라 **검사가 없어서**다. 구분하지 않으면 게이트 3이 보증한다고 말하는 내용이 조용히 비고, 사용자는 타입체크·테스트가 통과한 줄 안다.

### 게이트 3의 사후 감사 — 베이스라인 필드

게이트 3은 **베이스라인이 돌지 않았을 것**을 요구하는데, 채택이 끝나면 worktree는 폐기되고 브랜치만 남는다. 근거가 어디에도 안 남으면 나중에 "이 브랜치가 게이트 3을 통과한 게 맞나"를 확인할 방법이 없다 — **검증 못 하는 게이트는 게이트가 아니다.**

- 리포트에 **항상** 싣는다(채택 여부와 무관): `베이스라인: 미측정` 또는 `베이스라인: 측정됨 (<사유>)`. 채택하지 않은 실행에서도 게이트가 왜 막혔는지가 읽혀야 한다.
- **채택 커밋 메시지에도 싣는다.** 리포트는 같은 타깃 재실행에서 덮어쓰이고 `artifacts/`는 보존 상한에 밀리며 worktree는 폐기된다 — **커밋만 남는다.** 사후 감사가 가능한 유일한 자리다.

### 금지

- **자동 머지·자동 push** — 어떤 조건에서도
- **사용자 현재 브랜치에 직접 커밋 · 체크아웃**
- **채택 브랜치의 rebase·`--onto`** — 검증 기준점을 옮기는 어떤 조작도 금지. rebase하면 검증 결과가 무효가 되는데 브랜치는 여전히 "검증됨"을 주장하게 된다 — **최악의 조합이다**
- **기존 브랜치 덮어쓰기·force update** — 브랜치명이 곧 "이 커밋 위에서 이 타깃을 검증했다"는 주장이다. 같은 이름에 다른 내용을 넣으면 주장과 내용이 어긋난다. 충돌 시 채택하지 않고 `채택 안 함 (동일 브랜치 존재: <이름>)`으로 남긴다

### base 신선도 — 게이트가 막지 못하는 누수

worktree는 `base_sha`에서 생성되고 검증은 **그 커밋 위에서** 이뤄진다. 리허설은 수십 분이 걸리고 그동안 사용자는 작업 브랜치를 계속 진행한다 — **머지 시점의 트리는 검증된 트리가 아니다.**

게이트 4개로는 이걸 못 막는다. 막는 대신 **드러낸다**:

1. `base_sha`를 **브랜치명과 리포트 양쪽에 박는다** (`rn-upgrade/0.86.2-a3f9c21`). 브랜치만 봐도 어느 커밋 위에서 검증됐는지 알 수 있어야 한다. **자릿수는 자리마다 다르다** — 브랜치명·worktree 경로는 7자리(`worktree_path_template`의 `<base_sha7>`), **리포트 본문은 전체 SHA**다. 규칙과 사유는 `references/report-format.md` §헤더에 있다.
2. **머지 커맨드를 단독으로 주지 않는다.** 선행 확인 커맨드와 한 블록으로 낸다.

```sh
# 검증 기준: a3f9c21e4b8d7f0a2c5e9b1d6f3a8c4e7b0d2f59
git log --oneline a3f9c21e4b8d7f0a2c5e9b1d6f3a8c4e7b0d2f59..HEAD   # 비어 있지 않으면 아래 경고 적용
git merge rn-upgrade/0.86.2-a3f9c21
```

3. 리포트에 고정 문구를 싣는다(base가 최신이어도 출력):

> 이 브랜치는 `<base_sha>` 위에서 검증됐다. 그 이후 커밋이 있으면 머지 결과는 검증된 트리가 아니다 — 재리허설을 권장한다.

**실행은 사용자 몫이다.**

## 7. 리포트

**`references/report-format.md`를 Read해서 그대로 따른다.** 구조·경로·재현 블록 규칙·보존이 거기 있다.

모든 리포트는 다음을 고정 출력한다:

> 이 리포트는 **시도한 범위 안에서 관측된 사실**만 담는다. 전 티어 통과는 "업그레이드해도 된다"는 뜻이 아니라 **"자동으로 검사 가능한 지점에서는 멈추지 않았다"**는 뜻이다. 인증 이후 화면·런타임 회귀·실기기 동작·성능은 검사 범위 밖이다.

## 8. degrade — 4경로

**degrade는 판정이 아니다.** 판정 어휘는 3값(통과·실패·미실행) 그대로고, 아래는 그 판정을 **낼 수 있는지**에 관한 것이다. 4번째 어휘를 만들지 않는다.

| # | 조건 | 결과 | 위치 |
| - | --- | --- | --- |
| 1 | `shared/constants.md` 도달 실패 | **실행 거부** (아래 특례) | 출력만 |
| 2 | `shared/lockstep-sets.md` 도달 실패 | 인자 검증 3을 `미실행`으로 두고 진행 | 헤더 |
| 3 | `node -e` registry 조회 실패 | 인자 검증 1을 `미실행`으로 두고 진행 | 헤더 |
| 4 | `.rn-upgrade-kit/` 쓰기 실패 | 아래 «산출물 쓰기 실패» | 헤더 · 출력 |

### 1 — 상수 도달 실패는 이 스킬에서만 실행 거부다

자매 두 스킬은 상수를 못 읽어도 **관측을 그대로 내고** 상수에 기대는 판정만 `확인 못 함`으로 둔다. 이 스킬은 다르다:

- **상수가 판정 임계값이 아니라 실행 파라미터다.** `step_timeout_*` 없이는 단계를 돌리다 무한정 멈추고, `boot_survival_seconds` 없이는 T2 통과 조건 자체가 정의되지 않으며, `worktree_path_template` 없이는 격리 공간을 어디에 만들지도 모른다. **실행이 성립하지 않는다.**
- **지어내면 실행 전체가 근거 없는 판정이 된다.** advisory 스킬의 추정값은 한 줄을 틀리게 하지만, 여기서는 수십 분을 돌린 리허설이 무엇을 검증한 것인지 알 수 없게 된다.
- **`확인 못 함`은 이 스킬의 어휘가 아니다.** 3값 고정을 깨지 않으려면 남는 선택지는 거부뿐이고, **거부는 판정이 아니다**(§0) — 티어를 시작하지 않고 리포트 파일도 만들지 않는다.
- 사유 문구: `실행 거부 — 상수 도달 실패: shared/constants.md`. 그 파일의 «이 파일에 도달하는 법»이 정한 `Glob` 폴백을 **먼저 시도한 뒤에만** 이 결론을 낸다.

2를 같이 거부로 다루지 않는 이유는 `shared/lockstep-sets.md`가 **한 검사의 재료**일 뿐 실행 파라미터가 아니기 때문이다. 못 읽어도 티어는 그대로 돈다.

### 4 — 산출물 쓰기 실패

**쓰기 순서를 못박는다: 채택 커밋 → `artifacts/` → 리포트.** 리포트가 마지막인 이유는 **앞의 실패를 리포트가 보고할 수 있어야** 하기 때문이다. 반대 순서면 리포트가 이미 나간 뒤에 증거물 복사가 깨져 **리포트가 인용하는 경로가 거짓이 된다.**

| 실패 | 처리 |
| --- | --- |
| `artifacts/` 쓰기 실패 | **판정은 바뀌지 않는다.** 로그 경로 인용을 빼고 발췌만 싣는다 + 헤더에 `artifacts 쓰기 실패: <사유> — 전체 로그 없음` |
| 리포트 파일 쓰기 실패 | 리포트 본문을 **그대로 출력**하고 첫 줄에 `리포트 파일 쓰기 실패: <경로> — 아래가 리포트 전문이다` |

- **증거물을 못 썼다고 관측을 버리지 않는다.** `artifacts/`는 증거물이지 판정 근거가 아니다(§4) — 없어도 티어 판정은 이미 관측된 사실이다.
- **리포트를 못 썼다고 채택을 되돌리지 않는다.** 커밋은 검증이 끝난 결과물이고, 게이트 3의 사후 감사 근거는 커밋 메시지에 이미 들어 있다(§6).
- **쓰기 실패는 실행 거부가 아니다.** 거부는 티어 시작 전에만 한다(§0) — 이미 돌린 리허설의 관측을 파일 문제로 폐기하는 쪽이 더 나쁘다.

- **셸 분기·병기·폴백이 없다.** 재현 블록은 **POSIX 하나**, 셸 감지 로직 없음. Windows 미지원의 직접 결과다.
- **CI를 호출하지 않는다.** `gh workflow run`·폴링·리모트 push는 전부 스킬 밖 — README 문서로만 안내한다.
- **"안전하다"는 결론을 내지 않는다.** 스킬은 관측만 낸다.
